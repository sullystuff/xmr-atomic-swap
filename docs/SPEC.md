## 0. Terms

| Term | Meaning |
| --- | --- |
| Taker, maker | The taker takes a published offer. The maker runs the always-on daemon. |
| Direction A | Taker pays SOL, USDC or ETH and receives XMR. "Sell XMR" from the maker's side. |
| Direction B | Taker pays XMR and receives SOL, USDC or ETH. "Buy XMR" from the maker's side. |
| Locker (L) | The party that escrows the chain asset and can refund it. A: taker. B: maker. |
| Claimer (C) | The party that locks XMR and can claim the chain asset. A: maker. B: taker. |
| Asset | The escrowed chain asset. Solana: `0` = SOL, `1` = USDC. Ethereum: token address, `address(0)` = ETH. |
| Market | `sol`, `usdc_sol`, `eth`, `usdc_eth`. |
| `xmr` | Piconero (10^-12 XMR), `u64`. |
| `amount` | Escrowed asset in base units (lamports, wei, 10^-6 USDC). |
| Spend share `s`, commitment `S` | One party's half of the Monero spend key, and `S = s·G`. Revealing `s` on-chain is what a claim or a keyed refund does. |
| View share `v` | One party's half of the Monero private view key. Not a safety secret. |
| Chain time | Solana: `Clock.unix_timestamp`. Ethereum: `block.timestamp`. Every deadline uses chain time in seconds. Clients never use the local clock for a deadline. |

### 1.5 Conventions

- Amounts are `bigint` in atomic units in TS and decimal strings in JSON. Never `number`.
- Binary values in JSON are lowercase hex without `0x`, except EVM addresses and `bytes32` in EIP-712 JSON, which keep `0x`.

- Package names: `@xmrswap/core-wasm`, `@xmrswap/protocol`, `@xmrswap/sdk`, `@xmrswap/relay`, `@xmrswap/rebalancer`, `@xmrswap/daemon`, `@xmrswap/console`, `@xmrswap/web`, and the test-only `@xmrswap/svm-rpc` (`tools/svm-rpc`), `@xmrswap/e2e` (`tests/e2e`), `@xmrswap/deploy` (`deploy`). `pnpm-workspace.yaml` lists `packages/*`, `apps/*`, `tools/*`, `tests/e2e`, `deploy`.

- No secrets in the repository: API keys and RPC URLs are named by environment variable only.

## 2. Cryptography and encodings

All of this section is implemented **once**, in `crates/swap-core`, and reached from TypeScript through `@xmrswap/core-wasm`. The Solana program and the Ethereum contract re-implement only the verification halves they need, and prove agreement by consuming the vectors of section 2.12. TypeScript MUST NOT re-implement anything here except the pure-JS Monero transaction scan of section 2.11 and the standard-primitive calls the SDK makes with `@noble/*` on bytes the core produced: Ed25519 signing and strict verification of the 190-byte advance approval, Ed25519 signing of Solana transactions with a derived session or operator seed, and SHA-256 of an envelope for `in_reply_to`. EIP-712 signing and recovery are viem's, with the digest cross-checked against the core on every call. M3 packages do none of this themselves: they call `@xmrswap/sdk`.

### 2.1 Primitives

| Symbol | Definition |
| --- | --- |
| `G` | ed25519 basepoint, compressed `58 66 66 … 66` |
| `ℓ` | `2^252 + 27742317777372353535851937790883648493` |
| `n` | secp256k1 group order |
| `SHA256`, `SHA512` | FIPS 180-4 |
| `keccak256` | Ethereum's Keccak (also Monero's `cn_fast_hash`) |
| `DS(tag)` | The ASCII bytes of `xmrswap/v1/` followed by `tag`, followed by one `0x00` byte |
| `clamp252(b)` | 32 bytes `b` with `b[31] &= 0x0f`, read little-endian. Always `< 2^252 < ℓ < n`. |
| `wide(b)` | 64 bytes read little-endian, reduced mod `ℓ` |
| `chain_tag` | `0x01` Solana, `0x02` Ethereum |
| `swap_ref` | 32 bytes naming a swap. Solana: the swap PDA address. Ethereum: `swapId` (section 5.3). Both are computable before the lock transaction is sent. |

The protocol hash is **SHA-256** everywhere a hash is checked on both chains (it is a syscall on Solana and a 60-gas precompile on Ethereum). keccak256 appears only where Ethereum or Monero force it: EIP-712, the Merkle key pool, address derivation.

### 2.2 Key shares

A spend share is a **252-bit integer** `0 < s < 2^252`, not "random mod ℓ". That bound is below both group orders, so the same 32 little-endian bytes are a canonical Monero scalar, a valid secp256k1 scalar, and the only opening the Solana program accepts (it rejects `s + ℓ`). A view share is any canonical nonzero scalar mod `ℓ`.

Derivation (HKDF-SHA256, RFC 5869):

```
okm(label) = HKDF(ikm = seed[32], salt = DS("kdf"), info = label ‖ 0x00 ‖ chain_tag ‖ share_id[16], L = 64)

spend   s = clamp252(okm("spend")[0..32])            reject and treat the share_id as burned if s == 0
view    v = wide(okm("view"))                        reject if v == 0
session   = okm("session")[0..32]                    Solana: ed25519 seed. Ethereum: 1 + (big-endian(okm("session")[0..48]) mod (n − 1))
enc     e = okm("enc")[0..32]                        X25519 static secret (clamped by X25519 itself)
```

| Party | `seed` | `share_id` | State needed to avoid reuse |
| --- | --- | --- | --- |
| Taker | The 32-byte seed in the recovery file | The swap's `swap_nonce` (16 random bytes chosen by the client) | None. A fresh random nonce per swap makes every share fresh, and the tab can re-derive everything from the seed plus the nonce stored in the swap account. |
| Maker | The daemon keystore seed | 16 random bytes generated per share and **written to the database before the share is published or used** | The database row. A restored old database generates new random ids, so it cannot re-issue an old share. |

**Contact key.** Messages that concern no swap (a quote request, an approval request, a general inbox message) use a per-maker taker key so a reloaded tab can read the replies: `share_id = SHA256(DS("contact") ‖ maker PDA)[0..16]`, `chain_tag = 0x01`, key = `okm("enc")`.

Never reuse a spend share: every swap publishes one of the two. The `chain_tag` in `info` keeps Solana and Ethereum shares disjoint.

### 2.3 Point validation

`is_valid_key_commitment(P)`: `P` is the canonical encoding of a non-identity point in the prime-order subgroup. Implementation on Solana (2,750 CU, research ran it against 18 bad and 356 good points): reject the identity, compute `T = (ℓ−1)·P` with `multiply_edwards`, compute `−T` with `subtract_edwards(identity, T)`, require `−T == P` bytewise. `sol_curve_validate_point` alone is **not** sufficient (it accepts small-order, torsioned and non-canonical points). Lift `curve.rs` from `solana-curve.md` section 2.

Every spend commitment is validated: on-chain at the instruction that stores it (Solana), inside DLEQ verification (Ethereum), and again by each client before it derives the joint address.

`scalar_matches(s, S)`: `s` canonical and `s·G == S` (one `multiply_edwards`, 2,208 CU; the syscall refuses non-canonical scalars).

### 2.4 Proof of knowledge of a spend share (Solana)

A Schnorr proof that the author of `S` knows `s`. It stops a party from publishing a share it cannot open (which would make the counterparty's record show a fault it did not cause) and closes the rogue-key construction `S' = k·G − S_other`.

```
ctx  = 32 bytes: the maker PDA for a maker's share; the swap PDA for a taker's share
k    = wide(SHA512(DS("pok-nonce") ‖ s ‖ S ‖ ctx))
R    = k·G
c    = clamp252(SHA256(DS("pok") ‖ R ‖ S ‖ ctx))
z    = k + c·s mod ℓ
pok  = R[32] ‖ z[32]                                    64 bytes
verify: z canonical, and z·G == R + c·S                 (multiply_edwards ×2, add_edwards ×1; about 5,000 CU)
```

The Solana program verifies the proof on-chain for every share it stores (`refill_keys`, `post_quote`, `lock`, `take`, `approve`, `fund`). On Ethereum the DLEQ proof of section 2.6 plays this role and is checked off-chain. The challenge is clamped rather than reduced so the program needs no big-integer reduction. `add_edwards` exists in `solana-curve25519` 2.3.13 but its CU cost was not measured.

### 2.5 Joint Monero address

```
S = S_maker + S_taker                 v = v_maker + v_taker mod ℓ            V = v·G
address = monero_base58( varint(prefix) ‖ S ‖ V ‖ keccak256(varint(prefix) ‖ S ‖ V)[0..4] )
prefix: mainnet 18, stagenet 24, testnet 53. Regtest uses 18.
```

Always a standard address, never a subaddress or integrated address. Both view shares must be canonical and nonzero and their sum nonzero; a client that sees otherwise treats the swap as unusable. Monero base58 is the 8-byte-block variant (11 characters per block, 7 for the final 5 bytes). Each client recomputes the address from the four halves and never trusts one sent by the other side. The joint wallet is not a seed wallet: restoring it in standard wallet software needs address, private view key and private spend key ("generate from keys"). A full vector is in `monero.md` section 1 and is the first case of `joint_address.json`.

### 2.6 Ethereum twin keys and the cross-curve DLEQ proof

Ethereum has no ed25519 precompile, so each spend share also has a secp256k1 twin `P = s·G_secp`, and the contract checks the revealed integer against two address-form commitments:

```
keyAddr  = address(P)            = last 20 bytes of keccak256(X ‖ Y)
keyAddr2 = address((T2·s)·G_secp)   with T2 = uint256(keccak256("xmr-atomic-swap/twin-key/2")) mod n
```

On-chain check (`Secp256k1KeyCheck.mulVerify2`, about 7,300 gas; lift the library from `eth-keycheck.md` section 1): `0 < s < 2^252`, both commitments nonzero, and `ecrecover(0, 27, Gx, s·Gx mod n) == keyAddr`, likewise with `s·T2` for `keyAddr2`. Call the precompile directly; do **not** route through OpenZeppelin `ECDSA` (its low-s rule breaks the trick). The second address lifts the collision bound from 2^80 to 2^160; it is this project's own construction and is on the audit list.

The proof that `P` and `S` hide the same 252-bit integer is `sigma_fun` 0.9.0 `CrossCurveDLEQ<HashTranscript<Sha256, ChaCha20Rng>>` with second generators BIP-341 NUMS `0250929b74c1a04954b78b4b6035e97a5e078a5a0f28ec96d547bfee9ace803ac0` (secp256k1) and Monero's `H` `8b655970153799af2aeadc9ff1add0ea6c7251d54154cfa92c173a0dd39c1f94` (ed25519). Lift the snippet from `eth-keycheck.md` section 2.

**Proof size.** The real figure is **56,613 bytes**: the proof serialised with bincode 2 "standard" configuration over serde, measured in the research. The "about 112 kB" in the protocol note is eigenwallet's comment about the same proof in CBOR, where serde writes every byte of a byte array as a separate integer, roughly doubling it. (The CBOR size was not re-measured here; the factor of two is what that encoding produces.) This specification fixes bincode, so 56.6 kB is the number to plan around.

Wire format of a proof blob:

```
DleqBlob = 0x01 ‖ S[32] ‖ P_compressed[33] ‖ proof (bincode 2 standard)          56,679 bytes
```

Verifier rules: total length `<= 60,000` bytes; version byte is 1; bincode decoding consumes every remaining byte; `sys.verify(proof, (P, S))` is true (this also rejects an `S` outside the prime-order subgroup); then the verifier **computes** `keyAddr` and `keyAddr2` from `P` itself and compares them with the on-chain values. `dleqVerify` also requires `S` to be canonically encoded, since blobs are named by the hex of `S`. A proof is fetched and stored by the hex of `S`. Proofs carry no context binding; that is acceptable because shares are one-time and the maker's are committed under its signature (section 2.7).

Measured cost: native prove 65 ms, verify 63 ms; wasm32 prove 190 ms, verify 197 ms.

Who verifies what, and when (Ethereum swaps only):

| Proof | Verified by | Before |
| --- | --- | --- |
| Maker's share (leaf of the quote's key pool) | Taker's browser | Sending `lock`. The UI refuses to lock without a verified proof. |
| Maker's share supplied in `fund` (direction B; there is no pool) | Taker's browser | Showing the joint address or sending any XMR. The blob is fetched by `S_M`; the `dleqVerify` output MUST equal `makerSpendPub`, `makerKey`, `makerKey2` read from contract storage at the `finalized` tag. On failure the page never shows the address and tells the user to wait for the maker's refund (the take deposit is then returned or held under the normal rules). |
| Taker's share | Maker's daemon | Sending `approve` (direction A) or `fund` (direction B). Without it the daemon rejects with reason 1 (section 3.7). |

Without the direction-B row a maker could fund with `spendPub = x·G − S_T` and unrelated twins, collect the taker's XMR with `x`, and refund with a scalar that opens nothing.

A blob proves a statement, not who made it. The daemon MUST reject a taker commitment equal to any share in its own `key_shares` table, and the taker MUST reject a maker share equal to its own.

### 2.7 Merkle key pool (Ethereum quotes)

A signed Ethereum quote for direction A commits to a pool of the maker's one-time shares by Merkle root; the proofs travel off-chain.

```
leaf_i  = keccak256( keccak256( abi.encode(uint32 i, address keyAddr, address keyAddr2, bytes32 S) ) )
node    = keccak256( min(a, b) ‖ max(a, b) )            (sorted pair, as OpenZeppelin MerkleProof)
pool size is a power of two, 2 to 256 leaves; default 64; leaves in index order
proof   = sibling hashes, bottom-up
```

The contract verifies with `MerkleProof.verifyCalldata`. A share is consumed when the swap is **approved**, not when it is locked, so pending locks reserve no key. Consumption is tracked by `keyAddr` (`keyUsed[maker][keyAddr]`), not by leaf hash, so the same share placed at another index of a later pool is still refused; `fund` marks and checks the same mapping. The daemon signs a new root when half the pool is consumed. Takers obtain the leaves from the maker's pool route (section 6.3), recompute the root and build their own Merkle proof.

### 2.8 Message encryption

The maker publishes one X25519 public key with a version number in its Solana maker account (section 4.2). The taker uses a one-time X25519 key per swap (`enc` in section 2.2), recorded in the swap at lock time together with the maker key version it used. Both sides derive keys from that one Diffie-Hellman result, so a swap keeps working through any number of maker key rotations as long as the daemon still holds the private key of the recorded version (section 7.11).

The maker's public key of the version the taker used is **copied into the swap** (`maker_enc_key`), so the notice stays decryptable from chain state plus the recovery seed after any number of rotations.

```
dh      = X25519(own secret, peer public)              reject an all-zero result
K(use)  = HKDF(ikm = dh, salt = DS("ecdh"), info = use ‖ 0x00 ‖ taker_pub[32] ‖ maker_pub[32], L = 32)
uses    : "t2m" (taker to maker messages), "m2t" (maker to taker), "notice" (the lock notice)
cipher  : XChaCha20-Poly1305, 24-byte random nonce
```

**Envelope** (inbox messages, quote requests, approval requests, replies; on-chain or over Tor):

| Offset | Size | Field |
| --- | --- | --- |
| 0 | 2 | Magic `58 53` ("XS") |
| 2 | 1 | Version = 1 |
| 3 | 1 | Flags: bit 0 set = sent by the maker |
| 4 | 4 | Maker encryption key version, u32 LE |
| 8 | 32 | `taker_pub`: the non-maker party's X25519 public key. This is the "key for the reply". |
| 40 | 32 | `swap_ref`, or zeros when the message concerns no swap |
| 72 | 24 | Nonce |
| 96 | n + 16 | Ciphertext and tag. Associated data = bytes 0..72. Key = `K("t2m")` or `K("m2t")` by flag. |
| end | 64 | Only when flag bit 0 is set: Ed25519 signature by the maker's Solana operator key over `DS("envelope-sig") ‖ bytes[0 .. end−64]` |

Size caps: 900 bytes when posted on Solana, 16,384 bytes over Tor. The plaintext is UTF-8 JSON (section 6.1); it is never hashed, so JSON canonicalisation does not matter.

Public keys that are low-order Curve25519 points (14 encodings, frozen in `points.json`: the seven u-coordinates 0, 1, the two of order 8, p−1, p, p+1, and each with bit 255 set; the rule is "clear bit 255, compare with the seven") are refused on-chain wherever an encryption key is stored (`register_maker`, `rotate_enc_key`, `lock`, `take` on Solana, error `InvalidEncryptionKey`). Otherwise a taker could name a key that makes the Diffie-Hellman result zero, leaving the maker unable to build a notice and forcing an abort or a recorded fault at no cost. The Ethereum contract does not check this; the daemon rejects such a lock with reason 1.

A message naming a key version that is neither the maker's current version nor its previous version before `prev_enc_key_expires_at` is rejected with error `stale_key`; the client re-reads the registry and sends again.

**Lock notice** (fixed size, stored in the swap account or emitted in the Ethereum event):

```
notice_commitment = SHA256( DS("notice") ‖ swap_ref ‖ txid[32] ‖ v_C[32] )
notice_ct[104]    = nonce[24] ‖ XChaCha20-Poly1305( key = K("notice"), aad = swap_ref, plaintext = txid ‖ v_C )
```

`txid` is the 32 bytes of the Monero transaction id as its hex string reads. `v_C` is the claimer's private view share. The locker's view share is posted in clear at lock or fund time; neither half alone reveals anything. **Evidence** is the opening `(txid, v_C)` posted in clear; with it anyone can compute the joint view key and check the Monero chain. No salt is needed: `v_C` is a fresh 252-bit secret. The locker MUST check that the decrypted `(txid, v_C)` opens `notice_commitment`; a ciphertext that does not decrypt or does not open the commitment is treated as "no lock".

### 2.9 Solana: advance approvals and taker-bound quotes

**Advance approval.** An Ed25519 signature by the maker's operator key over the raw bytes below, presented on-chain as an Ed25519 precompile instruction in the same transaction (section 4.6). All integers little-endian. The message is exactly 190 bytes.

| Offset | Field | Type | Notes |
| --- | --- | --- | --- |
| 0 | `DS("sol-approval")` | 24 bytes | |
| 24 | `cluster_tag` | [u8; 32] | `Config.cluster_tag` (the genesis hash) |
| 56 | `program_id` | [u8; 32] | |
| 88 | `maker` | [u8; 32] | Maker PDA |
| 120 | `taker` | [u8; 32] | The only wallet that may use it |
| 152 | `asset` | u8 | `0`, `1`, or `0xff` = any |
| 153 | `direction` | u8 | `0` = A, `1` = B, `0xff` = any |
| 154 | `max_xmr` | u64 | Largest single swap, in piconero |
| 162 | `not_before` | i64 | Chain time |
| 170 | `expires_at` | i64 | Valid while `not_before <= now <= expires_at` |
| 178 | `epoch` | u32 | Must equal `maker.approval_epoch` |
| 182 | `approval_id` | u64 | Random; for logs |

An advance approval is reusable until it expires. Revocation is by epoch: bumping `approval_epoch`, or changing the operator key, kills every outstanding approval. The program reads the fields **out of the precompile instruction's message bytes**; they are not repeated as instruction arguments.

**Taker-bound quote** (oversized swaps). Not a signed blob: the operator posts it on-chain with `post_quote`, which creates a small `Quote` account (section 4.2) that the taker's `lock` or `take` consumes and closes. Sending the quote fields once, in the maker's transaction, keeps the taker's transaction well inside the 1,232-byte limit and needs no signature check or replay window. The quote is single-use by construction, expires at `expires_at` (at most 120 s after posting; valid while `now <= expires_at`), and dies when `quote_epoch` is bumped.

Validity fields (`valid_secs`, `expires_at`, `validUntil`) are **inclusive** on both chains (`now <= limit`). Protocol deadlines (`T_*`, section 3.2) are half-open. Boundary cases for both are in the vectors.

### 2.10 EIP-712 objects signed by the maker's Ethereum operator key

Domain: `EIP712Domain(string name,string version,uint256 chainId,address verifyingContract)` with `name = "XmrAtomicSwap"`, `version = "1"`, `verifyingContract` = the proxy address. Use `EIP712Upgradeable`.

```solidity
struct Quote {
    address maker;            // the maker's registered (owner) address
    address taker;            // address(0) = public quote; otherwise bound to this taker
    address token;            // address(0) = ETH
    uint8   direction;        // 0 = A, 1 = B
    uint8   approvalMode;     // 0 auto, 1 window, 2 advance approval required
    uint64  minXmr;
    uint64  maxXmr;
    uint64[3]  tierXmr;       // price tiers: tier i applies when xmr >= tierXmr[i]; tierXmr[0] == 0
    uint256[3] tierPrice;     // token base units per 1 XMR; 0 = tier unused (unused tiers trail)
    uint64[3]  depthXmr;      // depth tiers, same rule; depthXmr[0] == 0
    uint8[3]   depth;         // Monero confirmations; 0 = tier unused
    uint16  depositBps;
    uint32  approvalWindow;   // W_a
    uint32  noticeWindow;     // W_n
    uint32  claimDelay;       // D_c
    uint32  claimWindow;      // W_c
    uint32  finalWindow;      // W_f
    uint64  validUntil;       // valid while block.timestamp <= validUntil
    uint32  epoch;            // must equal the maker's quoteEpoch
    bytes32 keyRoot;          // Merkle root of the key pool (direction A); zero for direction B
    uint64  quoteId;          // cancel handle
}

struct Approval {
    address maker;
    address taker;            // must equal the lock's msg.sender
    address token;            // or 0xFFfFfFffFFfffFFfFFfFFFFFffFFFffffFfFFFfF = any token
    uint8   direction;        // 0, 1, or 255 = any
    uint64  maxXmr;           // largest single swap
    uint64  notBefore;
    uint64  validUntil;
    uint32  epoch;            // must equal the maker's approvalEpoch
    bytes32 approvalId;       // revocation handle
}
```

Type strings (the type hashes are their keccak256):

```
Quote(address maker,address taker,address token,uint8 direction,uint8 approvalMode,uint64 minXmr,uint64 maxXmr,uint64[3] tierXmr,uint256[3] tierPrice,uint64[3] depthXmr,uint8[3] depth,uint16 depositBps,uint32 approvalWindow,uint32 noticeWindow,uint32 claimDelay,uint32 claimWindow,uint32 finalWindow,uint64 validUntil,uint32 epoch,bytes32 keyRoot,uint64 quoteId)
Approval(address maker,address taker,address token,uint8 direction,uint64 maxXmr,uint64 notBefore,uint64 validUntil,uint32 epoch,bytes32 approvalId)
```

Prices are carried as `u128` everywhere off-chain (the compact form's width); a larger `tierPrice` is refused. Fixed-size arrays are encoded per EIP-712 as `keccak256` of the concatenated 32-byte element encodings. Signatures are 65 bytes `r ‖ s ‖ v`, verified with `ECDSA.recoverCalldata` (low-s enforced) against the maker's registered operator address. EOA operators only; no ERC-1271. Clients sign and verify with viem `signTypedData` / `verifyTypedData` using exactly these types; `interfaces/vectors/eip712.json` holds the typed-data JSON, digest and a signature from a fixed test key.

Use a validity of 120 to 180 s for Ethereum quotes; the UI refuses to submit with under 36 s left. Approvals are valid while `notBefore <= block.timestamp <= validUntil`. A quote with `taker != address(0)` is single-use: `lock`/`take` marks its `quoteId` cancelled.

**Compact form for the Solana board.** Ethereum quotes are published in the maker's `EthBoard` account on Solana for discovery (section 4.2). The Solana program treats them as opaque. The compact encoding is the struct fields in order, little-endian, with `address` as 20 bytes, `uint256` prices as u128, followed by the 65-byte signature. Clients expand it to the EIP-712 message, verify the signature against the operator registered in the Ethereum contract, and only then show the quote. Clients MUST discard a board quote whose `maker` field is not the Ethereum address mutually linked (section 5.6) to the board's owner; otherwise one maker could post another's quotes.

### 2.11 Monero lock verification and sweep

**Verification** is pure JavaScript (`@noble/*` only), the same file in Node and the browser: lift `lib/monero.mjs`, `lib/verify.mjs`, `lib/watch.mjs` from `tests/monero-regtest/` into `packages/sdk/src/monero/` as TypeScript. `verifyLock({ nodes, txid, viewPriv, spendPub, minAmount, minConf, minNodes })` returns `{ ok, state, reasons, amount, confirmations }` with `state` one of `not-found | invalid | pending | confirming | confirmed`.

Checked locally, where a node cannot lie:

1. The returned blob hashes to the txid (`keccak(keccak(prefix) ‖ keccak(rct_base) ‖ keccak(rct_prunable))`; pruned form accepted).
2. Exactly one output pays the joint address: `D = 8·v·R`, `P' = Hs(D ‖ varint(i))·G + S`, view tag checked first, additional tx keys handled.
3. The decrypted amount opens the output's Pedersen commitment, and is `>= minAmount`.
4. `unlock_time == 0` and RingCT type is 6.
5. No other output in the lock transaction or in its block carries the same one-time output key (`state = invalid`, reason `duplicate-output-key`). Two outputs with one key share a key image and only one can ever be spent.

Taken from nodes, so compared across them:

6. Every node returns the transaction in the same block (height and hash), and that block lists the txid. Confirmations = the **minimum** over all nodes that answered; a node without the transaction or with it only in its mempool counts as 0. `double_spend_seen` on any node blocks.

Node policy (clients and daemon): a list of two or more independently operated nodes, or exactly one node the user declares to be their own. `minNodes` = the list length. **Fail closed**: any disagreement or unreachable node means "not confirmed". Keep polling until the sweep itself is confirmed; confirmations can go down.

**Sweep** is `swap_core::sweep`, promoted from `tests/monero-regtest/rust-sweep` (monero-oxide `monero-wallet` 0.2.0; research ran it natively and in Chromium):

```rust
pub struct SweepParams {
    pub spend_key: [u8; 32],      // s_maker + s_taker mod ℓ
    pub view_key: [u8; 32],       // v_maker + v_taker mod ℓ
    pub lock_height: usize,
    pub lock_txid: [u8; 32],      // the verified lock transaction
    pub output_index: u64,        // index of the verified output inside that transaction
    pub destination: String,      // standard address or subaddress
    pub network: Network,
    pub max_fee: u64,             // piconero; the sweep fails rather than pay more
    pub publish: bool,
}
pub struct SweepOutcome { pub joint_address: String, pub txid: String, pub amount: u64, pub fee: u64, pub tx_hex: String, pub published: bool, pub ignored: Vec<(String, u64)> }
pub async fn sweep_joint<D: MoneroDaemonRpc>(daemon: &D, p: SweepParams) -> Result<SweepOutcome, SweepError>;
```

- The sweep spends **exactly the output named by `lock_txid` and `output_index`** and nothing else. The prototype spent every output to the joint address in the lock's block; whoever knows the address could then add dust outputs, or a second output with the same one-time key, and make the automated sweep fail or burn the real output. Other outputs to the joint address are reported in `SweepOutcome.ignored` and never spent automatically. `verifyLock` returns the `output_index` it verified.
- `max_fee` is new and mandatory: the prototype accepted any node-supplied fee rate. Callers pass `max(SWEEP_FEE_FLOOR = 2_000_000_000, amount × SWEEP_FEE_CAP_BPS / 10_000)` with `SWEEP_FEE_CAP_BPS = 50`. Both are named constants in `@xmrswap/protocol`; the regtest harness overrides them (regtest fees are far above mainnet's).
- The sweep is refused by consensus until the lock has 10 confirmations, whatever the swap's depth tier. The UI says "yours, spendable in N blocks".
- Node access needed (restricted RPC is enough): `/json_rpc`, `/get_height`, `/get_transactions`, `/get_o_indexes.bin`, `/get_output_distribution.bin`, `/get_outs.bin`, `/send_raw_transaction`. Browsers additionally need CORS on the node or the allow-listed proxy of section 6.5.
- The wasm transport wraps JS futures in `SendWrapper`; it is sound only on single-threaded wasm.

**Reference model.** `swap_core::model` is a pure implementation of the state machine of section 3: `fn apply(state: SwapState, call: Call, caller: Role, now: i64, env: &Env, consts: &ChainConsts) -> Result<Effects, ModelError>`. The model is the only oracle, so it is itself tested two ways inside `cargo test -p swap-core`: (1) a table test written by hand from sections 3.4 to 3.6, independent of the model's code; (2) a property test of rule 1 and of the exit invariant of section 3.2: for random parameters within the bounds and random call sequences at random times, never are secret-bearing calls by two different parties enabled at the same instant, and from every funded state each party with funds at stake has a call that becomes enabled.

Required sequences (minimum): a happy path per direction and mode; for each of `T_appr`, `T_note`, `T_cut` (B), `T_co`, `T_cd`, `T_final`, `T_exp`, `T_hold`, `T_split` the last enabled second and the first disabled second of every call it gates; direction B funded at the last second with `W_n` at its cap, then a notice at the last second, then ready at the last second (the latest reachable `T_cd` still precedes `T_final − 86,400`); direction B late notice followed by refund, and by claim at `T_co`; `refund` in ACTIVE after `T_note` (A); `expire_unnoticed` (B); a parked payout on each secret-bearing call followed by `withdraw_owed`; `D == 0` on every held-refund row; a counter at `u32::MAX`.

## 3. State machine

One escrow machine serves both directions and both chains. In locker/claimer terms it is identical; only who plays each role, the approval step, who owns the deposit and which counter moves differ. The Solana program and the Ethereum contract MUST implement exactly this section; `transitions.json` is its executable form.

**Per-swap parameters**, copied from the offer or quote at lock time and immutable afterwards.

| Symbol | Field | Default | Bound enforced at lock |
| --- | --- | --- | --- |
| `W_a` | approval window | 60 s (Ethereum: 120 s) | `30 <= W_a <= MAX_APPROVAL_SECS` when the swap can be PENDING; the UI warns above 60 s |
| `W_n` | notice window | 600 s Solana; 1,800 s Ethereum (10 min + `F`) | `MIN_NOTICE_SECS <= W_n <= MAX_NOTICE_SECS` |
| `W_p` | pending window this swap actually uses | derived | `W_a` when the swap waits for approval in window mode (or under `EXPLICIT_APPROVE`); `W_n` for direction B otherwise (the maker's funding deadline); 0 when the swap starts ACTIVE |
| `depth` (`d`) | Monero confirmations for this swap's size tier | tiers 2 / 10 / 25 | `1 <= d <= 255` |
| `Δ_cut` | `F + d × B + CUT_MARGIN_SECS` | Solana 1,275 / 2,715 / 5,415 s (about 21 / 45 / 90 min); Ethereum 2,460 / 3,900 / 6,600 s (41 / 65 / 110 min) at depths 2 / 10 / 25 | derived. `F` is included because the XMR locker must see its notice final before it broadcasts XMR; on Ethereum that alone takes 13 to 19 minutes. |
| `D_c` | claim delay, from the notice | "auto": the larger of 90 min (Solana) or 180 min (Ethereum) and the bound for the offer's deepest tier, rounded up to a minute. Solana at depth 25: 101 min. | `>= max(MIN_CLAIM_DELAY_SECS, Δ_cut + 2M)`. Solana: 3,600 / 3,600 / 6,015 s. Ethereum: 7,200 / 7,500 / 10,200 s. |
| `W_c` | claim window, from ready | 30 min Solana; 90 min Ethereum | `>= F + 2M` |
| `W_f` | final window, from lock | 7 days | `W_p + W_n + D_c + W_c + 86,400 <= W_f <= MAX_FINAL_SECS` |
| `dep_bps` | anti-spam deposit | maker's choice | `<= MAX_DEPOSIT_BPS` |

Arithmetic (all integer; u128 intermediates on Solana):

```
A:  amount = ceil (xmr × price / 10^12)      must be <= the taker's max_pay
B:  amount = floor(xmr × price / 10^12)      must be >= the taker's min_receive
deposit D  = floor(amount × dep_bps / 10^4)  A: part of amount.  B: posted separately by the taker (the "take deposit")
fee        = floor(amount × FEE_BPS / 10^4)  only on a claim
split      = ceil(D / 2) to the taker, floor(D / 2) to the treasury
price(xmr) = price of the highest used tier with xmr >= tier threshold;  depth(xmr) likewise
```

`price` is asset base units per 1 XMR. Tiers are well formed when `above[0] == 0`, tier 0 is used, used thresholds strictly increase and unused tiers trail; anything else is `TiersInvalid`, except a size with no used depth tier, which is `DepthInvalid`.

**A swap whose `amount` or `xmr` is zero is refused on both chains** (`AmountOutOfRange`). Direction B rounds down, so a dust take can compute to zero; such a swap would lock the taker's XMR against nothing. The reference model, the Solana program (`lock`, `take`, `post_quote`), the Ethereum contract and the SDK's pricing all refuse it.

### 3.2 Deadlines, invariants and the two rules that remove races

Every deadline is derived from an on-chain event time and stored in the swap. Sources:

```
t_lock                                   lock (A) or take (B)
T_pend  = t_lock + W_p                   approval deadline (A, "T_appr") or funding deadline (B, "T_fund"); PENDING only
t_A     = approval time (A), fund time (B), or t_lock when the swap starts ACTIVE          t_A < T_pend (or t_A = t_lock)
T_note  = t_A + W_n                      the notice is due before T_note
t_N     = notice time                    A: t_N < T_note.   B: t_N < T_nl (a notice at or after T_note is "late")
T_cut   = t_N + Δ_cut                    client auto-refund cutoff; in B also the first second a maker refund holds the deposit
T_co    = t_N + D_c                      claim-without-ready opens; the locker's ordinary refund closes
t_R     = ready time                     t_R < T_co
T_cd    = t_R + W_c                      claim window closes; the locker's fault refund opens
T_final = t_lock + W_f                   the claimer may claim in any post-notice state
T_nl    = T_final − D_c − W_c − 86,400   latest notice (direction B only; A uses T_note)
T_exp   = T_final + EXPIRY_SECS          the claim closes for good; the locker may refund
T_hold  = t_refund + HOLD_SECS           T_split = t_refund + SPLIT_SECS
```

**Derivation.** From the bounds of section 3.1:

```
T_note  = t_A + W_n  <= t_lock + W_p + W_n  <=  T_nl                (because W_f >= W_p + W_n + D_c + W_c + 86,400)
t_N     <  T_nl                                                      in both directions
T_co    = t_N + D_c  <  T_final − W_c − 86,400
T_cut   = t_N + Δ_cut  <=  T_co − 2M                                 (because D_c >= Δ_cut + 2M)
T_cd    = t_R + W_c  <  T_co + W_c  <  T_final − 86,400
T_final <  T_exp
```

So the order `t_lock <= t_A < t_N < T_cut < T_co`, `t_R < T_co`, `T_cd < T_final − 86,400 < T_final < T_exp` holds for every swap the contracts accept, including direction B funded at the last second with `W_n` at its cap. `W_n` is capped and `W_p` is the window actually used precisely so that this holds; `deadlines.json` and the sequences of section 2.12 exercise the extremes on both chains. As defence in depth, every row gated by `T_note`, `T_cut`, `T_co` or `T_cd` is also refused when `now >= T_final`, although the bounds make that unreachable.

**Invariant 1, exclusive windows (contracts).** Every interval is half-open `[from, to)`. The boundary second belongs to the later window: a deadline `T` means "allowed while `now < T`", and whatever opens at `T` is allowed from `now >= T`. In every state and at every instant at most one party can submit a call that reveals a secret:

| State | Interval | Secret-bearing call enabled |
| --- | --- | --- |
| ACTIVE (no notice) | any | Locker refund only. The claimer can never claim without a notice. |
| NOTICED | `[t_N, T_co)` | Locker refund |
| NOTICED | `[T_co, T_final)` | Claimer claim |
| READY | `[t_R, T_cd)` | Claimer claim |
| READY | `[T_cd, T_final)` | Locker refund |
| ABORTED | `[.., T_final)` | Locker refund |
| NOTICED, READY, ABORTED | `[T_final, T_exp)` | Claimer claim |
| NOTICED, READY, ABORTED | `[T_exp, ∞)` | Locker refund |

**Invariant 2, every funded state has an exit for each party with funds in it.** No party's funds ever depend on the other party acting.

| State | Taker's exit | Maker's exit |
| --- | --- | --- |
| PENDING | `cancel_pending` at any time; anyone's `expire_pending` after `T_pend` | Nothing of the maker's is escrowed |
| ACTIVE, direction A | `refund` at any time (A10a before `T_note`, A10g after); anyone's `refund_unnoticed` after `T_note` | Nothing escrowed; no XMR was broadcast (the notice comes first) |
| ACTIVE, direction B | For XMR already paid: `post_notice` until `T_nl`, then the claim paths. For the take deposit: anyone's `expire_unnoticed` at `T_exp`. | `refund` at any time |
| NOTICED, READY, ABORTED | A: `refund` in its windows and again from `T_exp`. B: `claim` from `T_co` or `T_final` | A: `claim` in its windows. B: `refund` in its windows and again from `T_exp` |
| HOLD, WITHHELD | Anyone's `release_deposit` at `T_hold`; anyone's `split_deposit` at `T_split` | The deposit is never the maker's |

**Rule 2, broadcast margins and finality (clients and daemon).** A failed transaction still publishes its arguments. A secret that lands late gives the counterparty both keys once its own window opens. Therefore:

- Never broadcast a secret-bearing transaction later than `M` before the boundary that opens the counterparty's window (`T_co`, `T_cd`, `T_final`, `T_exp`).
- Never act on state that is not final: the maker claims only after `ready` is finalized; the XMR locker sends XMR only after the escrow and its own notice are finalized. On Ethereum "finalized" means the block is at or below the `finalized` tag and the receipt's block hash is still canonical.
- Simulate before sending a secret; never skip preflight. On Ethereum send secret-bearing transactions through a private relay when one is configured.

### 3.3 States

| # | State | Meaning |
| --- | --- | --- |
| 1 | PENDING | A: funds escrowed, awaiting the maker's approval. B: take deposit posted, awaiting the maker's funds. Reserves no key share. Reserves no capacity either, except a direction-B take outside window mode, which holds `capacity_xmr` until it is funded or lapses (the maker is bound to fund it). |
| 2 | ACTIVE | Both spend commitments fixed, escrow funded, notice clock running. (A: "approved". B: "funded".) |
| 3 | NOTICED | Lock notice on-chain. The locker is verifying the XMR. |
| 4 | READY | The locker confirmed the XMR lock. |
| 5 | ABORTED_FREE | The claimer waived its claim until `T_final`; a refund will not hold the deposit. |
| 6 | ABORTED_HOLD | As above, but a refund holds the deposit. |
| 7 | HOLD | Refunded; the deposit is still in escrow until `T_hold`. |
| 8 | WITHHELD | The maker withheld the deposit. |
| 9 | DONE | Settled. On Solana the account stays, holding the revealed scalar, until closed (section 4.5). |

Value 0 means "no such swap". On Ethereum swaps are never deleted: rows marked "closed" below end in DONE there, and a `swapId` can never be reused. `outcome` records the counter id (section 3.7) of the transition that settled the swap. `deposit_state`: 0 none, 1 held, 2 withheld, 3 returned, 4 released by the maker, 5 split.

Notes:

- A7a and A8 are the only keyless refunds after approval. They exist only where no notice was ever accepted, so the contract treats the XMR as never locked. This is what makes "approved, no notice" safe to walk away from. The daemon therefore MUST have its notice accepted and final before it broadcasts XMR.
- A keyed refund is valid in ACTIVE at every instant: one sent before the notice that lands after it is A10b, and one that lands after `T_note` with no notice is A10g with the same result as the keyless A8. That race never produces a failed, secret-leaking refund.
- After an abort the maker's claim returns at `T_final` (A11c). An abort is a waiver until the final deadline, not forever; otherwise an absent taker would strand the maker's XMR.
- The claim pays the payout address in the maker's record (set by the cold owner key), never the operator.

Notes:

- A maker refund returns `amount` to the maker's **current operator address** on both chains (the hot wallet that funds direction-B escrows; for tokens, its associated token account). Direction-A claims go to the payout address.
- Every maker refund reveals `s_M`, so a taker who really locked XMR recovers it with its recovery file whenever the maker refunds. There is no keyless refund of the maker's escrow in direction B.
- **A late notice is still accepted** (B6 until `T_nl`). Without that, a taker whose payment was made but whose notice landed a second after `T_note` would depend forever on the maker choosing to refund; a vanished maker would lock the XMR and the escrow for good. With it the taker always reaches NOTICED and the claim paths. Lateness costs the taker only its protection against a withheld deposit: any maker refund after a late notice holds `Dp` (B9b, B9h). The maker's `refund` is valid in ACTIVE and in NOTICED alike, so a refund racing a late notice never fails.
- B11 returns a take deposit that would otherwise be stranded when neither side acts after funding. The maker's `amount` is parked, not lost.
- **Order of the taker's steps.** The taker pays from its own Monero wallet, so the txid is known only after broadcast. The page shows the joint address only once the swap is ACTIVE and the maker's escrow is final, then finds the payment by view-key scan (or a pasted txid) and posts the notice at zero confirmations. This is safe for the XMR because of the previous note; only `Dp` is at risk if the notice is late (B9b). The page MUST refuse to show the address with less than 180 s left before `T_note` (Ethereum: 600 s, because the notice is an L1 transaction). On Ethereum it MUST first verify the maker's DLEQ proof for the funded share (section 2.6).
- The maker's daemon MUST verify the lock and either `set_ready` at depth or `refund` in `[T_cut, T_co − M]`. Missing that window lets a taker with a false notice claim the escrow at `T_co` (B10b). This is the daemon's hardest deadline.
- The maker's free option (fund, watch the price, refund before `T_cut`) is visible as `backouts_post_notice` and costs the taker time and two Monero fees. It follows from "no maker bond".

### 3.6 Deposit sub-machine (both directions)

Entered by every refund marked "held". `T_hold = t_refund + HOLD_SECS`. `T_split = t_refund + SPLIT_SECS`.

| Call | Caller | Gate | Funds | Counter | To |
| --- | --- | --- | --- | --- | --- |
| `release_deposit` | Anyone | HOLD, `now >= T_hold` | `D` to the taker | `deposits_returned` | DONE |
| `release_deposit` | Operator | HOLD before `T_hold` | `D` to the taker | `deposits_returned` | DONE |
| `release_deposit` | Operator | WITHHELD, any time | `D` to the taker | `releases` | DONE |
| `withhold(evidence)` | Operator | HOLD, `now < T_hold`. Direction A with a notice on record: `evidence = (txid, v_M)` MUST open the notice commitment. Otherwise no evidence. | none | `withholds`; `withheld_volume += D` | WITHHELD |
| `split_deposit` | Anyone | WITHHELD, `now >= T_split` | `ceil(D/2)` to the taker; `floor(D/2)` to the treasury (or burned, section 4.1 `split_mode`) | `splits` | DONE |
| `publish_evidence(txid, v_C)` | The claimer (A: operator; B: taker wallet or session) | NOTICED or later, any state including DONE; must open the commitment | none | none | unchanged; sets the evidence fields and flag |

Invariants (each MUST have a test):

- No call can pay `D` to the maker, its payout address or its operator. The only destinations are the taker and the treasury (or burn).
- Fault refunds and free refunds (A7a, A8, A10d, A10e, A10f; B9a, B9c, B9g) never enter HOLD, so a maker that was provably late cannot withhold.
- `withhold` is refused at or after `T_hold` even if nobody has cranked `release_deposit`. The taker never races the maker.
- `T_split` is fixed at the refund.

### 3.7 Fee and counters

**Fee.** `fee = floor(amount × 5 / 10,000)` on every claim (A11a-c, B10a-c). Never on refunds, held deposits or pending cancels. It is deducted from the claimer's payout, so the party receiving SOL, USDC or ETH pays: the maker in A, the taker in B. It accrues in a contract-owned treasury balance and can never block a claim. The treasury's half of a split goes to the same place and is not a fee.

**Counters.** Kept per maker, per chain, in a `[u32; 40]` array. Each transition increments exactly one of the counters below (ids are the same on both chains and are also the `outcome` codes), and every transition emits an event carrying the swap id and the counter id. **Counter and volume updates saturate; they MUST NOT be able to fail any instruction** (a `claim` or `refund` that reverted on an overflowing counter would have published its secret).

| Id | Counter | Id | Counter | Id | Counter | Id | Counter |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 0 | `locks` | 8 | `completed` | 16 | `aborts_late` | 24 | `refunds_unconfirmed` |
| 1 | `takes` | 9 | `claims_without_ready` | 17 | `backouts_pre_notice` | 25 | `taker_missed_claims` |
| 2 | `approvals` | 10 | `claims_after_final` | 18 | `backouts_post_notice` | 26 | `taker_aborts` |
| 3 | `rejections` | 11 | `missed_notices` | 19 | `taker_claims_without_ready` | 27 | `expired_refunds` |
| 4 | `approval_timeouts` | 12 | `missed_claims` | 20 | `taker_cancels_approved` | 28 | `deposits_returned` |
| 5 | `pending_cancels` | 13 | `missed_funds` | 21 | `taker_refunds_noticed` | 29 | `withholds` |
| 6 | `notices` | 14 | `aborts_pre_notice` | 22 | `refunds_after_abort` | 30 | `releases` |
| 7 | `readies` | 15 | `aborts_early` | 23 | `taker_no_notice` | 31 | `splits` |

Id 32 is `rejections_no_fault`; ids 33 to 39 are reserved. `reject` takes a reason byte: 0 = the maker's choice (`rejections`); 1 = unusable taker input (Ethereum: no valid DLEQ proof, a low-order encryption key, a commitment equal to one of the maker's own); 2 = the named pool leaf was consumed by another swap. Reasons 1 and 2 increment `rejections_no_fault` and are left out of the approval rate. The reason is the maker's own statement; the UI shows both counts so a maker cannot hide ordinary rejections there unnoticed.

Counter 13 (`missed_funds`) is reachable only where `EXPLICIT_APPROVE` is false, that is on Solana.

Plus `u64` totals: `response_secs_sum`, `volume[asset]`, `withheld_volume[asset]`.

Provable maker faults are ids 11, 12, 13. Clients derive: approval rate `approvals / (approvals + rejections + approval_timeouts)`; mean response time `response_secs_sum / approvals`; withhold rate `withholds / (withholds + deposits_returned)`; unreleased rate `(withholds − releases) / withholds`. Clients merge the counters of a maker's linked Solana and Ethereum records. Refunds are fee-free, so a maker trading with itself can inflate `approvals` and `deposits_returned` at transaction-fee cost. Clients MUST therefore show fault, withhold and unreleased figures as absolute counts and relative to `completed` (the only counter that costs the 0.05% fee), next to the ratios above.

### 3.8 The three approval modes

| Offer or quote mode | No advance approval presented | Valid advance approval presented | Taker-bound signed quote |
| --- | --- | --- | --- |
| 0 AUTO | A: ACTIVE at lock, key share taken from the offer pool. B: PENDING with `T_fund = t_take + W_n`; a lapse is the fault `missed_funds`. | same as left | n/a |
| 1 WINDOW | PENDING with `T_appr`/`T_fund = t + W_a`. Reject, cancel and expiry are full refunds with no fault. | Treated as AUTO for this swap | n/a |
| 2 ADVANCE | The lock is refused (`ApprovalRequired`) | Treated as AUTO for this swap | n/a |
| Quote | n/a | n/a | Treated as AUTO; the key share comes from the quote; offer size limits do not apply, contract floors and caps do |

Where `EXPLICIT_APPROVE` is true (Ethereum), the table still decides whether the lock is accepted, but every accepted swap starts PENDING with `W_p = W_a`, every lapse counts as `approval_timeouts` (so a lapsed take is recorded there, not as a fault), and the daemon approves automatically after verifying the taker's DLEQ proof. The UI labels such offers "auto-accept" and shows the maker's measured response time.

Rules common to all modes: a pending lock reserves no key and (apart from a direction-B take outside window mode) no capacity; the taker can cancel a pending lock at any time for a full refund; an approval never overrides price, terms, size limits or capacity; the window length is per offer, the UI warns before locking on any window above 60 s and states how long funds may be held.

### 3.9 Session key

Created in the page (derived, section 2.2), named in `lock`/`take`, which the taker's wallet signs. That signature is its only authorisation. It is valid for that one swap and may call: A: `cancel_pending`, `set_ready`, `refund`, `close_swap`. B: `cancel_pending`, `post_notice`, `abort`, `claim`, `publish_evidence`, `close_swap`. The taker's wallet can call everything the session key can. It can never choose a destination: every payout goes to the taker address stored at lock. It pays its own fees from a budget forwarded by `lock`/`take`, and the leftover returns to the taker (sections 4.5 and 5.4). It does not replace the spend share: a keyed call needs both.

### 3.11 Obligations the contracts cannot enforce

Taker client: (1) fresh `swap_nonce` per swap and a saved recovery file before locking; (2) check the offer against `terms_hash`, show deposit, claim delay, approval window and the maker's rates before locking; (3) on Ethereum verify the maker's DLEQ proof before locking (A) and before showing the joint address or sending XMR (B); (4) check that the decrypted notice opens its commitment, then verify the lock fully (section 2.11); at depth before `T_cut` call `set_ready`, at `T_cut` otherwise call `refund`; (5) never broadcast a refund after `T_co − M` or `T_final − M`, or a direction-B claim after `T_cd − M`; (6) direction B: claim only after `ready` is final; (7) read time from the chain.

Maker daemon: (1) fresh share per swap, row written first; (2) direction A: build the XMR transaction, post the notice, see it final, then broadcast; if the swap is no longer ACTIVE/NOTICED, do not broadcast; (3) send XMR only after the taker's escrow is final; (4) claim only after `ready` is final and never later than `T_cd − M`; simulate first; (5) direction B: verify the taker's lock, `set_ready` at depth, otherwise `refund` in `[T_cut, T_co − M]`; (6) decide withholds inside the hold and attach the evidence; release on request; (7) if its own lock fails or is reorged out, `abort` at once; (8) before `post_notice` (A) and before `set_ready` (B), re-read the swap at `finalized` and require the stored commitments to be the ones it verified, otherwise `abort` (A) or `refund` (B).

### 3.12 Binding approvals to the lock they act on

`approve`, `fund` and `reject` name a swap by its id only. A taker could replace a pending lock with another at the same id (Solana: cancel and re-lock at the same PDA; Ethereum: a short reorg, since the daemon must approve before finality) carrying a different size or different key commitments, and the maker's transaction would apply to a lock its rules and proof checks never saw. So each of the three takes `expected_open: [u8; 32]` and fails with `BadState` unless it equals the swap's open hash:

```
Solana    SHA256( DS("open") ‖ swap PDA ‖ t_lock (i64) ‖ direction ‖ asset ‖ xmr (u64) ‖ amount (u64) ‖ deposit (u64)
                  ‖ taker_spend_pub ‖ locker_view as stored at lock (zeros in B) ‖ taker_enc_key ‖ maker_enc_key )
          recomputed by the program from the account; nothing extra is stored.
Ethereum  sha256( abi.encodePacked( "xmrswap/v1/open", bytes1(0), swapId, uint64 tLock, uint8 direction, address token, uint64 xmr,
                  uint256 amount, uint256 deposit, bytes32 takerSpendPub, address takerKey, address takerKey2,
                  bytes32 takerView, bytes32 takerEncKey, bytes32 makerEncKey, bytes32 keyLeaf ) )
          computed in lock/take and stored as openHash.
```

### 3.13 Conventions the reference model fixes

The vectors encode these, so both contracts and the SDK share them.

- **Check order:** direction, caller, state (and open hash), time gate, then secret or evidence. Each rejected vector row breaks one rule only.
- **`TooEarly` versus `TooLate`:** a call refused only because of the time is `TooLate` if one of its windows in that state has already closed, otherwise `TooEarly`.
- **The extra `now >= T_final` refusal** of section 3.2 applies to rows with an upper gate. Rows that open at `T_note` and have none (A8, A10g, B9b) stay enabled after `T_final`; otherwise invariant 2 would fail.
- **"Closed" rows** end in DONE in the model with `closed = true` when nothing was parked. Solana then closes the account in the same instruction (if the taker's wallet can hold the rent and, for USDC, the vault can be emptied; otherwise DONE and `close_swap` finishes); Ethereum keeps DONE.
- **Effective `mode`:** 3 for a quote; 2 when a valid approval is presented on a WINDOW or ADVANCE offer; otherwise the offer's mode. Only "is it 1" changes behaviour.
- **Wrong-direction calls:** `reject` in direction B outside window mode (Solana) is `BadState`; `approve` in B, `fund` in A, `refund_unnoticed` in B, `expire_unnoticed` in A are `WrongDirection`. A `reject` reason above 2 is `BadState`.
- **`deposit_state`:** `release_deposit` from HOLD sets 3 whoever calls; from WITHHELD sets 4; `split_deposit` sets 5. `t_refund` is written by every keyed refund, `t_settled` on reaching DONE.
- **`withhold`** where no evidence is required ignores (and does not store) supplied evidence. `publish_evidence` needs a notice on record and moves no counter (`0xff` in events).
- **Payouts of zero** are not listed or sent. B11 always parks the maker's `amount`.
- **Treasury shares on Ethereum** appear as a payout to `treasury` that is "accrued", never parked.

Caller rules that differ by chain, which the regenerated vectors express (Solana 405 rows, Ethereum 399; both contracts replay theirs with no special cases):

| Case | Solana | Ethereum |
| --- | --- | --- |
| `lock`/`take` sent by someone other than the taker | `Unauthorized` (the transaction lacks the taker's signature) | Cannot be expressed: the taker **is** `msg.sender` and `swapId = keccak256(taker, nonce)`. The call opens the sender's own swap under another id. No such row is generated. |
| `withdraw_owed` by an account that is owed nothing | `Unauthorized` | `NothingOwed` (the function pays the caller's own parked balance) |
| `claim`/`refund` by a third party holding the secret | `Unauthorized` | Succeeds; pays the stored party |

Program name `xmr_swap`, Anchor 0.32.1, one crate in `solana/program`. ### 4.4 Opening a swap

**`lock(args: LockArgs)`** (direction A). Signer: taker wallet.

```rust
pub struct LockArgs {                 // 247 bytes, 248 with an approval
    pub swap_nonce: [u8; 16],
    pub session_lamports: u64,        // forwarded to the session key
    pub asset: u8,
    pub xmr: u64,
    pub max_pay: u64,
    pub expected_terms_hash: [u8; 32],    // ignored with a quote
    pub min_seq: u64,                 // 0 = no check; ignored with a quote
    pub taker_spend_pub: [u8; 32],
    pub taker_pok: [u8; 64],          // ctx = swap PDA
    pub taker_view: [u8; 32],         // v_T, in clear
    pub taker_enc_key: [u8; 32],
    pub maker_enc_version: u32,
    pub key_hint: u8,                 // preferred pool slot; only a hint
    pub approval_ix: Option<u8>,      // index of the Ed25519 instruction carrying an advance approval
}
```

Accounts, in order (14): `taker` (signer, writable), `swap` (init), `maker` (writable), `config`, `session_key` (writable; its address is stored), `system_program`, `offer` (writable), `quote` (writable), `quote_rent_receiver` (writable; must equal `maker.operator`), `instructions_sysvar`, `mint`, `taker_token` (writable), `vault` (init), `token_program`. Exactly one of `offer` and `quote` is present; `quote_rent_receiver` accompanies `quote`; `instructions_sysvar` is present iff `approval_ix` is; the last four are present for USDC and absent for SOL. An absent account is passed as the program id (Anchor's optional-account convention).

Checks, in this order:

1. `maker.paused == 0`. `maker_enc_version` equals `enc_key_version`, or equals `enc_key_version − 1` with `now < prev_enc_key_expires_at`; else `StaleKeyVersion`. Copy that version's key into `maker_enc_key`.
2. `is_valid_key_commitment(taker_spend_pub)`; proof valid with `ctx` = swap PDA; `taker_view` is a canonical nonzero scalar; `taker_enc_key` is not a low-order point. `asset` matches the offer or quote, and the token accounts are present iff `asset == 1`.
3. **Against an offer:** direction is A; `enabled`; `now <= updated_at + valid_secs` (`OfferStale`); `seq >= min_seq`; `terms_hash == expected_terms_hash` (`TermsChanged`); `min_xmr <= xmr <= max_xmr`; `amount = ceil(xmr × price(xmr) / 10^12) <= max_pay` (`PriceMoved`); `depth = depth(xmr)`; the per-swap bounds of section 3.1 hold for that depth and for this swap's `W_p`.
   **Against a quote:** `quote.maker`, `quote.taker`, direction and asset match; `now <= expires_at` (`QuoteExpired`); `quote.epoch == maker.quote_epoch`; `args.xmr == quote.xmr`; `quote.amount <= max_pay`; terms, depth and the maker's share are taken from the quote; the account is closed, rent to the operator.
4. **Approval**, when present: verify as in section 4.6; taker, asset and direction match (or are `0xff`); `xmr <= max_xmr`; `not_before <= now <= expires_at`; `epoch == maker.approval_epoch`.
5. Decide the start state by section 3.8. If ACTIVE from an offer: take the first pool slot at or after `key_hint` (wrapping) that is filled and unused, mark it used, copy it to `maker_spend_pub` (`NoKeyAvailable` if none); `capacity_xmr -= xmr` (`CapacityExceeded`). If PENDING: `open_pending < MAX_OPEN_PENDING`, then increment it.
6. `session_lamports >= Rent::minimum_balance(0)` (a smaller transfer to a new address fails the transaction).

Implementation notes fixed by the vectors: a `lock`/`take` without the taker's signature fails with `Unauthorized`; every reason an approval does not admit the lock (not yet valid, expired, wrong asset, direction or bindings, over `max_xmr`, stale epoch, wrong key) is `ApprovalInvalid`, and `SignatureInstructionInvalid` is only for an instruction that is not one self-contained Ed25519 signature; both or neither of `offer` and `quote` is `BadState`; a quoted swap stores `price = 0`, ignores offer limits and capacity, and still verifies an approval if one is presented; `approve` consumes no capacity.

Effects: transfer `amount` into escrow (SOL: system transfer into the swap PDA; USDC: `transfer_checked` into the new vault); transfer `session_lamports` to the session key; write every field; `t_lock = now`; `t_final = now + w_f`; PENDING: `t_pending_deadline = now + w_a`; ACTIVE: `t_active = now`, `t_note_deadline = now + w_n`. Counter `locks`. Event `SwapOpened`.

**`take(args: TakeArgs)`** (direction B). Signer: taker wallet. Same 14 accounts.

```rust
pub struct TakeArgs {                 // 214 bytes, 215 with an approval
    pub swap_nonce: [u8; 16],
    pub session_lamports: u64,
    pub asset: u8,
    pub xmr: u64,
    pub min_receive: u64,
    pub expected_terms_hash: [u8; 32],
    pub min_seq: u64,
    pub taker_spend_pub: [u8; 32],

```

As `lock`, with the offer's or quote's direction B: `amount = floor(xmr × price / 10^12) >= min_receive` (quote: `quote.amount >= min_receive`). Only `deposit` (plus session lamports and rent) is transferred in. The start state is always PENDING; `t_pending_deadline = now + w_a` in window mode, `now + w_n` otherwise. Outside window mode from an offer, `capacity_xmr -= xmr`. `open_pending` is checked and incremented. Counter `takes`.

**`approve(expected_open, maker_spend_pub, maker_pok)`** (A2). Signer: operator. Accounts: `operator`, `swap`, `maker`, `config`. Checks `expected_open` (section 3.12); validates the share and proof (`ctx` = maker PDA). Sets ACTIVE, `t_active`, `t_note_deadline`.

**`fund(expected_open, maker_spend_pub, maker_pok, maker_view)`** (B5). Signer: operator. Accounts: `operator` (writable), `swap`, `maker`, `config`, `system_program`, then optional `mint`, `operator_token`, `vault`, `token_program`. Checks `expected_open`; validates as `approve`; `maker_view` canonical and nonzero; records `locker_view = maker_view`; transfers `amount` from the operator (SOL from the signer; USDC from the operator's token account) into escrow.

**Every exit from PENDING decrements `open_pending`**: `approve`, `fund`, `reject`, `cancel_pending`, `expire_pending`. A direction-B take outside window mode that is rejected, cancelled or lapses does not restore `capacity_xmr`; the next refresh resets it.

`taker`, `maker_wallet` and all destination token accounts are `UncheckedAccount`s validated by hand; typed accounts would make a missing destination revert the instruction. The token destinations are the associated token accounts of `swap.taker`, of `maker.payout` or `maker.operator`, and the treasury vault. For a USDC swap all six token slots must be filled; for SOL all six are absent (the program id, read-only).

**Addresses are requirements; destination state parks.** The `taker` account, the taker's associated token account, the Treasury PDA (or the incinerator for a burned SOL half) and the treasury vault are fixed at lock and must be the right addresses in every instruction, `claim` and `refund` included: a wrong one fails with `Unauthorized`, a token account missing from a USDC swap's instruction with `WrongAsset`. Otherwise anyone cranking a keyless instruction could force the taker's money to be parked by mis-naming an account; a simulation catches the caller's own mistake. Whether such an account exists, is initialised, frozen, executable or rent-exempt never fails anything. **The maker's destination is soft:** if `maker_wallet` or `maker_token` is not the address the instruction pays (`set_payout` or `set_operator` can land between a claim's simulation and its execution), the payout is parked for the owner.

**Pay or park (claims and refunds never revert on a payout).** `claim` and `refund` carry a secret in their arguments. If the transaction fails, the secret is public anyway and the escrow is still there for the other side. So these instructions, and for uniformity every instruction that pays out, do: verify, write state, emit, then for each payout:

- SOL: pay if the destination would hold at least its rent minimum afterwards and is not executable; otherwise add the amount to `owed_*`.
- USDC: pay with `transfer_checked` signed by the swap PDA if the vault is not frozen and the destination is the recipient's associated token account, owned by the Token program, 165 bytes, of the right mint and owner, initialised and not frozen; otherwise add the amount to `owed_*`. Payout paths never create a token account.
- Fees go to the Treasury PDA or the treasury vault under the same test.
- Counters saturate (section 3.7). Nothing after the secret check may fail except running out of compute or fee, which simulation catches.

`withdraw_owed(who)`: `who = 0` taker (signer: taker wallet; destination: any account it names), `1` maker (signer: maker **owner**), `2` treasury (anyone; destination pinned to the treasury). Pays the full owed amount and zeroes it. It does not create the destination token account (the list has no token-account program or payer): the caller puts an idempotent associated-token-account creation before it in the same transaction. May revert; it carries no secret. For `who = 0` the `taker`/`taker_token` slots are the destination; for `who = 1`, `maker_wallet`/`maker_token`.

**Keeping the revealed scalar.** After a claim the taker's XMR depends on reading the maker's scalar; after a refund the maker's depends on the taker's. Transaction history is pruned, so a settled swap account stays open with `revealed` readable through `getAccountInfo` from any RPC node.

`close_swap` closes the vault and the swap account, all rent to the taker, when `state == DONE`, all `owed_*` are zero, and one of:

- no secret was revealed (anyone);
- the caller is the party that did **not** reveal (A after a claim: taker or session; after a refund: operator. B mirrored), at any time;
- the caller is the taker (wallet or session) and `now >= t_settled + CLOSE_GRACE_SECS`.

A stranger can never close an account that holds a revealed scalar. Any token balance left in the vault (dust someone sent after settlement) is first moved to the treasury vault, or burned if that fails, so nobody can block the close.

Outcomes marked "closed" in section 3 (A3, A4, A5, A7a, A8, B2, B3, B4) close the account in the same instruction when nothing was parked; otherwise they end in DONE.

**Session key lamports.** A fee payer must end each transaction rent-exempt or at exactly zero. `lock`/`take` fund the session key with at least the rent minimum; `cancel_pending`, `refund`, `claim` and `close_swap` transfer every remaining lamport of a session-key signer to the taker as their last step (the fee is deducted before execution, so the key ends at zero). This transfer cannot fail the instruction either: if the taker account cannot hold the lamports (in practice only an executable account, since the sweep is always at least the rent minimum), they go to the swap account and return to the taker with the rent when the swap is closed. They are not added to `owed_taker`, which is in token units for a USDC swap. A key funded with exactly the rent minimum can never pay a fee, so the budget is the rent minimum plus one fee per transaction; the SDK default is the rent minimum plus 2,000,000 lamports. A refund that cannot pay its fee is a lost refund. A wallet-signed `refund`/`claim` does not sweep the key; `close_swap` signed by the key does. Inside a settling instruction the order is: token CPIs, the session sweep, then lamports moved by hand.

### 4.6 Verifying an advance approval

The transaction carries an Ed25519 precompile instruction; the program reads it through the instructions sysvar at `approval_ix` and requires all of:

- its program id is the Ed25519 program;
- its data declares exactly one signature;
- all three instruction-index fields of the offsets struct are `0xFFFF` (signature, key and message live in that same instruction);
- the public key bytes equal `maker.operator`;
- the message is exactly 190 bytes, begins with `DS("sol-approval")`, and its `cluster_tag`, `program_id`, `maker` and `taker` fields equal `Config.cluster_tag`, the program id, the maker PDA and the signing taker.

The remaining fields are read from the message at the offsets of section 2.9.

**Proven in M1.** WP2's spike verified the `sol_signed.json` instructions under LiteSVM 0.16.0 (with its `precompiles` feature), so the on-chain `Approval` account fallback is not needed and is not built. Clients need to know: with the two compute-budget instructions first, the Ed25519 instruction is index 2 (`approval_ix = Some(2)`); its data is header (2) ‖ offsets (14) ‖ key (32) ‖ signature (64) ‖ message (190) = 302 bytes; and the precompile's signature counts toward the fee, so a transaction with an approval pays for two signatures (10,000 lamports).

### 4.9 Constants, parameters and authority

- **Constants** (section 3.1) are `pub const` in `constants.rs`, mirrored in `@xmrswap/protocol` and checked by `deadlines.json`.
- **Per-offer parameters** are everything in `OfferTerms`. Deposits, delays and windows belong to the offer so they keep working after the program is frozen.
- **Measured compute** (the built program, SOL / USDC, asserted as ceilings): `lock` 38,000 / 47,900; `take` 40,900 / 46,300; `approve` 23,100; `fund` 25,800 / 29,600; `post_notice` and `set_ready` about 14,800; `claim` 25,100 to 27,200 / 33,900 to 36,000; `refund` 22,900 to 24,300 / 30,000 to 33,300; `close_swap` 18,700 / 23,400; `refill_keys` with 8 slots 73,700; `refresh_offers` with 4 offers and 4 Ethereum quotes 20,100. The SDK sets the compute-unit limit from simulation × 1.2 and never relies on the default.
- Errors where this document names none: a malformed argument (unknown mode, slot or `who`, a `refill_keys` batch of 0 or more than 8) is `InvalidArgument`; an account belonging to another maker is `Unauthorized`; `close_swap` of a swap that is not DONE or still owes something is `NotClosable`.
- **Upgrade authority**: the program launches upgradable under the project owner's key and is later made immutable with a verifiable build published. Both are owner steps outside this specification. The UIs display the current upgrade status read from the ProgramData account.
- LiteSVM's `add_program_from_file` writes a ProgramData account with **no** upgrade authority (checked in the 0.16.0 source). Tests of `initialize` therefore overwrite that account's metadata with a test authority through `set_account`; `tools/svm-rpc` exposes the same as `svm_setUpgradeAuthority`.

### 4.10 Transaction format and sizes

Every instruction fits a legacy transaction of at most 1,232 bytes with one signature and the two compute-budget instructions the SDK always adds. Hand-computed from the layouts above (65 bytes of signature section, 3 of header, 33 per account key plus 1, 32 of blockhash, 20 for the compute-budget instructions, and per instruction 4 bytes of framing plus one byte per account index plus the data):

| Transaction | Account keys | Bytes |
| --- | --- | --- |
| `lock`, SOL, against an offer | 9 | 683 |
| `lock`, USDC, against an offer | 13 | 811 |
| `lock`, USDC, against a `Quote` account | 14 | 843 |
| `lock`, SOL, with an advance approval (Ed25519 instruction of 306 bytes) | 11 | 1,054 |
| `lock`, USDC, with an advance approval | 15 | **1,182** (the largest single-swap transaction) |
| Two `lock`s, SOL, two makers | 13 | 1,084 |
| Two `lock`s, USDC, two makers, legacy | 18 | 1,244: **does not fit** |
| Two `lock`s, USDC, v0 with the protocol lookup table | 14 static | 1,156 |
| `claim`, USDC (Settle list) | 16 | 691 |
| `refresh_offers`, four offers and four Ethereum quotes | 9 | 1,097 |
| `refill_keys`, eight slots | 5 | 1,078 |
| `post_message`, 900-byte payload, with a swap account | 5 | 1,201 |

Rules that follow:

- A single `lock` or `take` is always a legacy transaction, with or without an approval or quote. `take` is 33 bytes smaller than `lock`.
- Batches (the large-swap tool): **two SOL legs per legacy transaction; one USDC leg per legacy transaction.** Three legs never fit. A leg that uses an advance approval travels alone.
- Optional optimisation, not required for correctness: two USDC legs fit a v0 transaction that loads `config`, the System program, the USDC mint and the Token program from a **protocol lookup table**. The table is created at deployment (an owner step) and its address pinned next to the program id; in tests `svm-rpc` creates one with `svm_createLookupTable`. v0 transactions and lookup tables were not run under LiteSVM 0.16.0; WP5 spikes this and falls back to one USDC leg per transaction if it does not work.
- The byte counts above are now measured, not estimated: a program test executes each transaction and an SDK unit test builds each and asserts its serialised length. The v0 two-leg USDC transaction (1,156 bytes, 14 static keys, a four-address lookup table) was run in `svm-rpc` by the SDK's integration suite. The taker UI still opens USDC legs one per transaction, because no protocol lookup-table address is pinned until a deployment exists.

## 5. Ethereum contract

One contract address, `XmrSwap` behind its proxy, in `ethereum/src/`, implementing `interfaces/ethereum/IXmrSwap.sol`. The code is three objects, because as one contract the runtime is 35,446 bytes against the 24,576-byte limit: `XmrSwap` (set-up, registry, views, one thin entry point per swap call, the reentrancy guard) and two **linked libraries** called by DELEGATECALL in the proxy's context, `SwapOpen` (`lock`, `take`, EIP-712 digests) and `SwapSettle` (every other transition). The ABI is unchanged. A deployment deploys the two libraries, the implementation and the proxy; an upgrade deploys a new implementation linked to its libraries. `forge` links automatically; deploying by hand needs the two library addresses. Names in the interface use `viewShare` where this document writes `view` (a reserved word in Solidity). Lift from `docs/research/prototypes/eth-keycheck/evm/` (section 1.6: `Secp256k1KeyCheck.sol`, the EIP-712 and Merkle-pool code, `_payout`, the upgrade tests) and `docs/research/eth-keycheck.md`. WP1 writes the complete `IXmrSwap.sol` (every function, event, error and struct below with full parameter lists; this section abbreviates some with "…"). The state machine is section 3 with `EXPLICIT_APPROVE = true` and the Ethereum column of the constants table. `block.timestamp` is the clock.

### 5.1 Structure

```solidity
contract XmrSwap is IXmrSwap, Initializable, UUPSUpgradeable, Ownable2StepUpgradeable,
                    EIP712Upgradeable, ReentrancyGuardTransient {
    constructor() { _disableInitializers(); }
    function initialize(address owner_, address treasury_, address usdc_) external initializer;   // __EIP712_init("XmrAtomicSwap", "1")
    function _authorizeUpgrade(address) internal override onlyOwner {}
}
// deployed (in tests only) as: new ERC1967Proxy(address(new XmrSwap()), abi.encodeCall(XmrSwap.initialize, (owner, treasury, usdc)))
```

- **UUPS**, not a transparent proxy. The contract becomes immutable when the owner calls `renounceOwnership()`.
- **The owner's only power is upgrading.** Treasury address, the USDC address and every constant are fixed at initialisation or in the implementation, so renouncing freezes them too.
- All state lives in one ERC-7201 namespaced struct, namespace `xmrswap.storage.v1`.
- `nonReentrant` on every function that moves funds. Tokens: `address(0)` (ETH) and the one USDC address only.
- `foundry.toml`: `solc = "0.8.31"`, `evm_version = "osaka"`, optimizer on (200 runs), `via_ir = true`, `ffi = true` (one test runs `cast wallet sign`), the interface imported through the remapping `xmrswap-interfaces/=../interfaces/`, remappings as in the research note, and `fs_permissions = [{ access = "read", path = "../interfaces/vectors" }]` so tests can read the vectors.
- `ethereum/lib/` (OpenZeppelin v5.7.0 both repositories, forge-std 1.17.0) is **vendored and committed** (`forge install --no-git`, pruned to the sources a build reads), so acceptance runs offline.
- `script/DeployAnvil.s.sol` deploys libraries, implementation, proxy and a mock USDC, writes `ethereum/deployments/anvil.json` (`chainId`, `proxy`, `implementation`, `usdc`, `owner`, `treasury`) and refuses every chain id but 31337.

Swaps are never deleted; a settled swap costs nothing to keep and its `revealed` value, nonce, notice ciphertext and evidence stay readable with `eth_call`. Counter and volume updates saturate.

**Storage is packed, and the layout is recorded in `ethereum/STORAGE.md`; it must not change once a proxy is deployed** (an upgrade may only append). The stored swap is an internal struct of 24 slots (`amount`, `deposit` and `price` as `uint128`; anything above `2^128 − 1` is refused with `AmountOutOfRange`); `lock` writes 17 fresh slots, `take` 13. `getSwap` returns the interface struct, so the ABI is unchanged. Measured gas for a whole transaction, ETH / USDC: `lock` 528,905 / 564,646; `take` 432,390 / 468,119; `approve` 98,293; `fund` 176,819 / 203,498; `postNotice` about 221,000; `setReady` about 67,900; `claim` about 110,500 / 130,200; `refund` after `T_cd` 126,291 to 162,817.

`lock` checks, in order: maker registered and not paused; quote signature recovers to `makers[q.maker].operator`; `block.timestamp <= q.validUntil`; `q.epoch == quoteEpoch`; not cancelled; `q.direction == 0`; `q.taker` is zero or `msg.sender`; token allowed; tier arrays well-formed; `minXmr <= xmr <= maxXmr`; `amount = ceil(xmr × price(xmr) / 1e12) <= maxPay`; all bounds of section 3.1 for `depth(xmr)`; mode 2 requires a valid `Approval` (signature, `taker == msg.sender`, token and direction match or are wildcards, `xmr <= maxXmr`, `notBefore <= now <= validUntil`, epoch, not revoked), otherwise pass an empty signature (a non-empty one is always verified; approval failures use `WrongParty`, `TokenNotAllowed`, `WrongDirection`, `AmountOutOfRange`, `Expired`, `StaleEpoch`, `Revoked`, and every signature failure is `BadSigner`); `amount != 0` (`AmountOutOfRange`); taker keys nonzero (`BadKey`) and `0 < view < ℓ` (in `take` the taker's view share must be zero); the leaf's Merkle proof verifies against `q.keyRoot` and its `keyAddr` is unused; `openPending < MAX_OPEN_PENDING`. `lock` writes the leaf's `key`, `key2` and `spendPub` into the swap provisionally, stores `swapNonce`, `makerEncKey` (as supplied by the taker; the daemon checks it against its own key of that version before approving), `openHash`, and appends the id to `swapsByTaker`. A taker-bound quote (`q.taker != address(0)`) is marked cancelled, so it is single-use. Funds: ETH needs `msg.value == amount + sessionBudget`; USDC needs `msg.value == sessionBudget` and pulls `amount` with `safeTransferFrom`, requiring the balance delta to equal `amount` (`ShortTransfer`). `sessionBudget` is forwarded to `sessionKey`. State PENDING, `tPendingDeadline = now + q.approvalWindow`. `take` mirrors it for direction B with `deposit` in place of `amount` and no leaf.

`claim` and `refund` are callable by anyone because the secret is the authorisation and the destination is fixed; copying a secret from the mempool gains nothing. The contract checks the session key (or the taker's wallet) as `msg.sender` only on `setReady`, `cancelPending`, and the direction-B `postNotice` and `abort`; the page still sends its automatic refund from the session key so no wallet prompt is needed.

### 5.4 Payouts never revert

`_payout(token, to, amount)`: ETH is sent with a 30,000 gas stipend; USDC with `SafeERC20.trySafeTransfer`. On failure, `owed[token][to] += amount` and `PayoutDeferred` is emitted. Parked payouts are keyed by the address the push would have gone to (the payout address for a direction-A claim, the current operator for a direction-B refund); B11 parks the maker's escrow for the maker's **owner** address. Because parking is per account, not per swap, `owedOf` is an account total. A transaction sent with too little gas for the stipend makes the push fail and the payout park; a third party can provoke that by front-running with a starved copy, which costs the recipient one `withdrawOwed` (a gas floor would instead turn it into a revert of a secret-bearing call). Fees and treasury halves only increment `treasuryAccrued`. Order inside `claim` and `refund`: verify the secret, write state, emit, then pay. A blacklisted recipient, a paused token or a recipient contract that rejects ETH therefore cannot make a secret-bearing call fail. If the escrow contract itself is blacklisted or USDC is paused, USDC swaps are stuck until the issuer acts; state stays consistent and the Monero leg still completes. The UI discloses this for USDC markets.

The session key is an ordinary externally owned account derived in the page. `lock`/`take` forward `sessionBudget` to it; the client returns what is left to the taker with a plain transfer when the swap closes. The SDK sizes the budget for four calls at `ETH_SESSION_GAS_PER_CALL = 271,000` (the dearest session call, `postNotice`, measured on anvil, plus 25%) at a capped gas price and shows it before locking; its integration suite re-measures on every run.

### 5.6 Identity link across chains

The Solana maker record names an Ethereum address (`eth_link`); the Ethereum record names a Solana owner key (`solanaOwner`). Each is written by a transaction from that chain's own key, and neither contract reads the other. Clients treat two records as one identity **only when both pointers are in effect and point at each other**; a one-sided pointer is ignored. Each record holds one pointer, so links are one to one. A change or removal takes effect after `LINK_DELAY_SECS` and is an event; clients keep history attached to both keys after an unlink, so a bad record cannot be shed.

## 6. Off-chain messages, transports and the relay

Nothing safety-critical depends on this section's transports: lock, approval, notice, ready, claim, refund, abort and evidence are always transactions on the swap's own chain. Messages carry requests and conversation; the one exception is the DLEQ proof for Ethereum swaps (section 6.4).

### 6.1 Message types

The plaintext inside an envelope (section 2.8) is a UTF-8 JSON object with a `t` field. Hex strings are lowercase; amounts are decimal strings.

| `t` | From | Fields | Reply |
| --- | --- | --- | --- |
| `quote_request` | taker | `chain` (`solana` or `ethereum`), `market`, `direction` (`A` or `B`), `xmr`, `taker` (address on that chain), `reply_to?`, `note?` | `quote_response` |
| `quote_response` | maker | `ok`. Solana: `quote_id` and `expires_at`; the maker has already posted the `Quote` account, which the client reads and checks. Ethereum: `quote`, the base64 of the 316-byte compact form with its signature (section 2.10), which holds every field including `taker` and `keyRoot`; the same fields as JSON would not fit the 900-byte cap. Direction A: the pool route serves the leaves of that `keyRoot`. | none |
| `approval_request` | taker | `chain`, `taker`, `market?`, `direction?`, `max_xmr?`, `reply_to?`, `note?` | `approval_response` |
| `approval_response` | maker | `ok`; on success the variable fields only (Solana: `asset`, `direction`, `max_xmr`, `not_before`, `expires_at`, `epoch`, `approval_id`; the client fills in `cluster_tag`, `program_id`, `maker`, `taker`. Ethereum: the `Approval` fields) and `sig` (base64) | none |
| `inbox` | taker | `text` (max 2,000 characters), `action?` (`release_deposit`), `reply_to?` | `inbox_reply`, possibly later |
| `inbox_reply` | maker | `text`, `in_reply_to` (SHA-256 of the request envelope) | none |
| `notice_copy` | claimer | `commitment`, `ciphertext` | `ack`. A faster duplicate of an on-chain notice; never a substitute. |
| `ack` | either | `in_reply_to` | none |
| `error` | maker | `code`: `stale_key`, `rate_limited`, `not_allowed`, `too_large`, `bad_request`, `unavailable`; `detail?` | none |

`reply_to` is the taker's Solana address. Replies that are not the immediate HTTP response (a later `inbox_reply`) are delivered two ways: the daemon keeps them for 30 days at the replies route of section 6.3, and, when `reply_to` is present, also posts them with `post_message` to that address. A swap-bound message needs no `reply_to` (the swap names the taker). The taker's key for swap-less messages is the contact key of section 2.2, so a reloaded tab can read them. The largest responses are checked against the 900-byte on-chain cap in `envelope.json`.

A lock notice is **not** a message: it is the `post_notice` transaction (104-byte ciphertext, section 2.8) on the chain that enforces the swap. For an Ethereum swap that is an Ethereum transaction; `notice_copy` may also be sent so the taker sees it sooner.

### 6.2 Transports

| Transport | How | Used when |
| --- | --- | --- |
| Solana (baseline) | `post_message` with the envelope as instruction data; the recipient account is the maker PDA (to a maker) or the taker's wallet (to a taker). Read with `getSignaturesForAddress` + `getTransaction`; follow with `logsSubscribe({ mentions })`. Cap 900 bytes. | Always available. Costs one transaction fee. Who messaged whom, and when, is public. |
| Tor | HTTP to the maker's onion service (section 6.3), through the relay or directly from Tor Browser. Cap 16,384 bytes. | Preferred when the maker lists an onion address. Falls back to Solana when unreachable. |
| Ethereum events | `postMessage` on the contract. Cap 900 bytes. | Fallback only, when the Solana RPC is unreachable. Costly. |

A reply from a maker is encrypted to `taker_pub`, has flag bit 0 set and carries the operator signature; the client verifies it against `maker.operator` from the registry before use. `envelopeOpen` enforces this: opening an envelope with flag bit 0 requires the operator key and fails with `EnvelopeBadSignature` otherwise. `envelopeHeader` reads the key version and `swap_ref` before a key is chosen. The daemon rejects an envelope naming an expired key version with `error: stale_key`.

### 6.3 Maker endpoint (served by the daemon; reached as an onion service)

Plain HTTP on a loopback port; a `torrc` hidden service maps onion port 80 to it. Responses carry `Access-Control-Allow-Origin: *` so Tor Browser can call it directly (that mode is untested).

| Route | Body | Response |
| --- | --- | --- |
| `GET /xs/v1/info` | | `{ maker, operator, enc_key_version, chain_time }` |
| `POST /xs/v1/msg` | Envelope, `application/octet-stream` | 200 with a signed reply envelope, or 4xx `{ code }` |
| `GET /xs/v1/dleq/<spend_pub hex>` | | The `DleqBlob` for one of the maker's shares, or 404 |
| `PUT /xs/v1/dleq/<spend_pub hex>` | `DleqBlob` (at most 60,000 bytes) | 204 if the blob verifies and its `S` equals the path; else 400. Kept 15 minutes unless a swap references it. |
| `GET /xs/v1/pool/<keyRoot hex>` | | `{ "leaves": [{ "index", "key", "key2", "spend_pub" }] }` for a key pool the maker has signed into a quote (at most 256 leaves, under 60,000 bytes), or 404. The client recomputes the root and builds its own proof. |
| `GET /xs/v1/replies/<taker_pub hex>` | | `{ "envelopes": [base64] }`: reply envelopes addressed to that key, newest first, kept 30 days. Ciphertext only. |

The daemon rate-limits per circuit and per taker key and enforces the size caps: 16,384 bytes on `/msg`, 60,000 bytes on `/dleq`. A contact of kind 5 (HTTPS blob endpoint) serves the `dleq`, `pool` and `info` routes.

### 6.4 DLEQ proof delivery (Ethereum swaps)

A proof is 56.7 kB (section 2.6): about 50 Solana transactions or roughly two million gas of calldata. It never goes on-chain. Consequences, all mandatory:

- A maker that enables an Ethereum market MUST list a blob endpoint: an onion address, or contact kind 5 (an HTTPS URL serving the same four routes). The console refuses to enable an Ethereum market without one.
- Taker, before `lock` (direction A): fetch the pool with `GET /xs/v1/pool/<keyRoot>`, check that the leaves hash to the quote's `keyRoot`, pick at random a leaf whose `keyAddr` is unused and not named by a currently pending lock, fetch `GET /xs/v1/dleq/<S>` for it, `dleqVerify`, and compare the returned `keyAddr`/`keyAddr2` with the leaf. Then `PUT` its own proof.
- Taker, direction B: `PUT` its own proof before `take`; after `fund`, fetch and verify the proof for the maker's funded share before showing the joint address (section 2.6).
- Maker, before `approve` or `fund`: the taker's proof is present and verifies against the commitments in contract storage; the taker's `makerEncKey` equals the maker's key of that version. Otherwise `reject` with reason 1. Before `fund` the maker's own proof for the share it is about to use MUST already be served.
- Ethereum swaps therefore cannot run on on-chain messaging alone. The UI says so when neither the relay nor a direct route to the maker's endpoint is available.

### 6.5 Relay (`packages/relay`)

A small Node service (express) that lets a browser on the ordinary internet reach onion services. It carries ciphertext and self-verifying blobs only.

| Route | Request | Behaviour |
| --- | --- | --- |
| `GET /relay/v1/status` | | `{ tor_ok, registry_age_secs, makers, monero_nodes: [{ ok, height }] }` |
| `POST /relay/v1/forward` | `{ onion, method, path, body_b64? }` | Forwards through the Tor SOCKS5 proxy (remote DNS) to `http://<onion><path>` and returns `{ status, body_b64 }` |
| `POST /monero/<n>/<path>` | Raw body | Optional allow-listed reverse proxy to the n-th configured Monero node |

Rules (each MUST have a test):

- **Not an open proxy.** `onion` must be the `onion` field of a maker account currently in the registry. The relay reads maker accounts with `getProgramAccounts` every 60 s and on a miss; it needs no key.
- `path` must match `^/xs/v1/(info|msg|dleq/[0-9a-f]{64}|pool/[0-9a-f]{64}|replies/[0-9a-f]{64})$`; `method` must be one that route defines.
- Caps on the **decoded** upstream body: 16,384 bytes for `/xs/v1/msg`, 60,000 bytes for `/xs/v1/dleq/*`; upstream responses up to 60,000 bytes. The relay's own request-body limit is 96 kB (a 56,679-byte proof is about 75.6 kB as base64 inside the JSON). A test forwards a real blob from `dleq.json`.
- Per-IP limits (default 60 requests and 4 MB per minute); 30 s upstream timeout.
- No message logs by default: no bodies, no onion addresses, no client IPs. A debug flag enables logging and prints a warning at start.
- Binds to `127.0.0.1` unless configured otherwise.
- The Monero proxy forwards only `/json_rpc` (methods `get_info`, `get_block`, `get_block_count`, `get_fee_estimate`), `/get_height`, `/get_transactions`, `/get_transaction_pool_hashes`, `/get_o_indexes.bin`, `/get_output_distribution.bin`, `/get_outs.bin`, `/send_raw_transaction`. A proxy counts as a node for trust purposes; two proxies run by one operator are one source.

Settings (`relay.toml`, found through `RELAY_CONFIG` or the working directory; each key has an environment override; all are in `packages/relay/relay.example.toml`): `bind` (127.0.0.1:8787), `tor_socks` (127.0.0.1:9050), `solana_rpc_url_env` (`SOLANA_RPC_URL`), `program_id` (**no default**; the release's id must be set), `monero_nodes` (none; `n` counts from 0), `monero_max_response_bytes` (16 MiB), `allowed_origins` (none), `trust_proxy_hops` (0), `debug_log` (false), `[rate_limit] requests_per_minute` (60), `bytes_per_minute` (4,194,304). The package exports `startRelay` and `loadConfigFromProcess` and a binary `xmrswap-relay`.

Behaviour M3 packages must allow for:

- **CORS is off by default.** A relay on another origin than the UI (another port counts) needs `allowed_origins` set to that origin, or both behind one reverse proxy. `*` on a localhost relay would let any page the user visits use it.
- **Errors** are `{ "error": code }`: 400 `bad_request`, `bad_onion`, `bad_path`; 403 `onion_not_listed`, `monero_path_not_allowed`, `monero_method_not_allowed`; 404 `not_found`, `no_such_node`; 405 `bad_method`; 413 `too_large`; 429 `rate_limited` (with `Retry-After`); 502 `upstream_unreachable`, `upstream_too_large`, `upstream_redirect`; 504 `upstream_timeout`. A maker's own refusal arrives as HTTP 200 with the upstream status inside `{ status, body_b64 }`. An upstream redirect is never followed or relayed.
- `body_b64` is required for `POST` and `PUT` and forbidden for `GET`.
- `tor_ok` means only that the SOCKS proxy answered a handshake; it does not prove Tor has bootstrapped. The UI labels it "Tor proxy reachable" and treats a successful forward to a maker's `/info` as the real test. `registry_age_secs` is −1 before the first read; a registry that cannot be refreshed is used for at most 10 minutes, then every forward is refused.
- The Monero proxy is `POST` only, never forwards a query string, and re-serialises `/json_rpc` bodies (one object, allow-listed `method`).

What the relay operator can see: the user's IP, which maker they contact, sizes and timing. Cannot: read, alter or forge messages, move funds, or block a refund (refunds go from the browser straight to the chain). If the relay is down the UI falls back to on-chain messaging.

## 7. Maker daemon

`packages/daemon`: one always-on Node 22 process on the maker's machine. It needs no inbound connectivity unless the Tor module is on. It holds the operator keys and the key-share seed; it never holds the cold owner keys. It uses `@xmrswap/sdk` for both chains and for Monero verification, `@xmrswap/core-wasm` (nodejs target) for all cryptography and for sweeping joint addresses, and `monero-wallet-rpc` only for the inventory wallet.

### 7.1 Modules (one per row of DESIGN's "Maker tools" table)

### 7.2 Configuration

One TOML file, validated with zod, with every change appended to a change log. Changes apply without a restart **except endpoints and keys**: a change under `[solana]`, `[ethereum]`, `[monero]` or `[daemon]` (other than `mode`, the priority fee, finality and CORS) is saved, logged, raises an alert and takes effect at the next start. Unknown keys are errors. `daemon config check <file>` validates without starting. **Both example files in `docs/DESIGN.md` MUST pass `config check` unchanged**, alone or concatenated; that is an acceptance test. To make that true:

- Every key has a default (shown in parentheses; where none is shown: `source` = `"coingecko"`, `deviation_pct` = 2.0, `max_xmr` = the largest ladder size, caps and limits = unlimited). Sections absent from the examples (below) are optional.
- `config check` evaluates **every bound of section 3.1** for every enabled offer on its chain and prints the effective values (for example the claim delay chosen by `"auto"`). A violated bound is an error.
- An Ethereum market enabled without a blob endpoint (as in DESIGN's example) is a warning that keeps that market off, not an error.
- A string of the form `<…>` is a placeholder: accepted by the schema, reported as a warning, and the feature that needs it stays off.
- A market whose `source` is `wxmr_pool` is accepted, but the Decisions table makes the pool a cross-check only: the loader promotes the first fallback to primary, uses the pool as that market's cross-check, and warns. With no fallback the market stays off.

### 7.3 Keys and custody

- `keystore.json` in `data_dir`, encrypted (scrypt + XChaCha20-Poly1305 through core-wasm) with the passphrase from `keystore_passphrase_env`: the key-share seed, the Solana operator key, the Ethereum operator key.
- Encryption private keys are random per version, stored in the database sealed with AES-256-GCM under a key derived from the keystore seed by HKDF (not `passphraseSeal`: scrypt per message would cost seconds), and deleted by the rotation module.
- The database is bound to the maker PDA and the inventory wallet's primary address at first start and refuses to open against others.
- Keep the Ethereum and Solana operator balances capped (`paying_caps`): a stolen operator key can commit that balance in direction B.

### 7.5 Swap handling

Chain watching: a filtered `programSubscribe` on the maker's swaps plus a full `getProgramAccounts` catch-up at start, on reconnect and every 60 s (Solana); `eth_getLogs` from a stored cursor plus a subscription, with state read at the `finalized` tag before acting (Ethereum). Verify the endpoint's genesis hash or chain id before trusting it.

Direction A, per swap:

1. See the lock. Solana: ACTIVE at `finalized`. Ethereum: PENDING; fetch and verify the taker's DLEQ proof, apply approval rules, `approve` with the open hash of the lock it examined, then wait until the `Approved` state is at or below `finalized` and **re-read the swap there**: the stored commitments must be the ones whose proof it verified, else `abort`.
2. Reserve a ladder output. Derive the joint address from `S_M`, `S_T`, `v_M` and the taker's `v_T` (in clear in the swap).
3. Ask wallet-rpc for the lock transaction **without relaying it** (`do_not_relay`, `get_tx_hex`); store raw hex, txid and inputs in `lock_txs`.
4. `post_notice` with the commitment and ciphertext. Wait until NOTICED is final.
5. Only then relay the transaction. If the swap left ACTIVE/NOTICED meanwhile, do not relay; thaw the output.
6. Until the lock is 10 deep and the swap is settled: check the lock on every configured node; if it has dropped out of the chain, rebroadcast the stored raw transaction; if its inputs were spent elsewhere, `abort`.
7. On READY (final): simulate, then `claim` no later than `T_cd − M`. Without ready: at `T_co`, by policy, `claim` (default when the lock is confirmed) or `abort`. After `T_final`: `claim`.
8. On a taker refund: read `s_T` from the swap account, sweep the joint address back to the inventory wallet once the lock has 10 confirmations, hand the output to the splitter, then `close_swap`. Run the withhold decision inside the hold.

Direction B, per swap:

1. See the take. Apply approval rules (Ethereum: verify the DLEQ proof). `fund` before `T_fund` from the operator balance, within `paying_caps`.
2. On the notice: decrypt it, check that it opens the commitment, derive the joint view key, `verifyLock` against every node with the swap's `xmr` and depth. Before `set_ready`, re-read the swap at `finalized` and require the taker's commitments to be the ones it verified at `fund`.
3. At depth: `set_ready`. If the lock is not confirmed at `T_cut`: `refund` at once, and never later than `T_co − M`. This timer has the highest priority in the process and raises an alert if any node is unreachable while it runs.
4. After the taker's claim: read `s_T`, sweep the joint address to the inventory wallet.

The sweep uses the daemon's most trusted node and the fee cap of section 2.11.

### 7.6 Restart recovery

On start, before quoting anything:

1. Open the keystore and database; check the bindings.
2. Load every non-terminal swap row. Fetch each swap's on-chain state at `finalized` and reconcile: the chain wins for state; the database wins for secrets, raw transactions and intents.
3. Resolve each `intents` row in `sent`: look the signature or hash up on-chain. Found: mark confirmed. Not found and its blockhash or nonce is dead: mark failed and let the state machine re-plan. Anything else: `needs_review`, alert, do not resend.
4. For each `lock_txs` row whose swap is NOTICED or later, check the lock on all nodes and rebroadcast if missing.
5. Recompute every deadline from on-chain timestamps and re-arm the timers; act immediately on any that have passed and are still actionable under rule 2.
6. Scan for swaps that name this maker but have no row (opened while the daemon was down) and treat them as new. A share whose row is missing is not usable: `abort` (A, pre-notice) or let the take lapse (B).
7. Only then resume `refresh_offers`. A stopped daemon's offers lapse by themselves through `valid_secs`.

Adapters hold no keys: they move funds only through `ExecContext`, which the daemon implements with the intent journal. None of this code runs in the console's browser. Adapters read API credentials from the environment by variable name at call time through an injectable reader (the daemon may pass its own, backed by the keystore) and never store or log them. A handle is `venue:…` and can embed a venue's per-order access token (FixedFloat), so the daemon treats handles as private.

**What the package owns and what the daemon supplies.** `@xmrswap/rebalancer` exports `Rebalancer` (routing by priority or best quote, per-venue, per-transaction and per-day caps, modes, the allow-list, test transfers, cooldowns, stall handling, the cost log; `tick()` advances open refills), `createAdapters(deps)` (builds the enabled adapters, each wrapped in an allow-list guard), `evaluateLevels` (a pure helper for level triggers) and the settings schema for `[rebalance]`. The daemon supplies: the `ExecContext`; a `StateStore` (`load`/`save` of one snapshot string); a `PriceSource` (`usd(asset)`); **the allow-list** (the schema default is empty and an empty list allows nothing, so the daemon passes the inventory wallet and the operator and payout addresses); for the bridge a `ReserveProofVerifier` (wallet-rpc `check_reserve_proof`) and optionally a `PoolDepthReader`; for the exchange `withdrawKeys` (payout address to the key name registered at the exchange); and an alert sink. Package defaults are the safe ones: `mode = "alert"`, every venue disabled, `rate = "float"`, `choose = "priority"`; unknown keys under `[rebalance]` are errors. A refill larger than a cap is cut to the cap. A failed or ambiguous refill keeps counting against `max_in_transit_usd` until the maker acknowledges it (`acknowledge`), and an ambiguous send is parked as `held` and never retried elsewhere.

Decisions the flows make where sections 3.11 and 7.5 left room (the daemon and the tab follow them by calling the flows, and MUST NOT second-guess them):

- A secret-bearing call is proposed only while it stays acceptable for `M − 1` more seconds: taker refund until `T_co − M` (NOTICED) or `T_final − M`; maker claim until `T_cd − M` (READY) or `T_exp − M`; direction-B taker claim until `T_cd − M` or `T_exp − M`; maker refund until `T_co − M` or `T_final − M`. Refunds in ACTIVE have no limit.
- A tab that comes back after `T_cut` and finds the lock confirmed at depth, with no refund yet sent, sets ready (allowed until `T_co`) instead of refunding.
- After `T_note` with no notice the taker sends the keyless `refund_unnoticed`, not the keyed refund.
- The maker relays its prepared lock only before `T_cut`; later it aborts. Without ready at `T_co` it claims if its own lock verifies as confirmed, otherwise aborts.
- In direction B with no notice at `T_note` the maker refunds at once.
- `close_swap` (Solana) is proposed once the caller has swept and nothing is owed.
- Reputation is merged for pairs currently linked both ways and for pairs that were ever linked: `rememberPastLinks` rebuilds link history from `LinkChanged` events on both chains (`linkChanges`, `linkIntervals`) into a `LinkMemory`. An RPC node that has pruned the maker's transactions yields a shorter history.
- **An explicit request wins.** A confirmed request from the user or the operator (refund, cancel, abort, reject, back out, withhold, release) takes precedence over every automatic step while the contract still accepts the call that carries it out (inside the broadcast margin for a secret). When it no longer can, the `Decision` carries `refused: <reason>` and says what happens instead. Reasons: `ready-already-set`, `refund-window-closed`, `abort-window-closed`, `already-settled`, `cannot-exit-after-funding`, `reject-not-available`, `hold-ended`, `no-deposit-held`. (Found as a bug by the end-to-end suite: a confirmed refund was once overtaken by `set_ready`.)
- `solanaInstruction` / `ethereumCall` turn a decision into the instruction or calldata; `SolanaClient.sendAndConfirm` polls (no WebSocket); `EthereumClient.owedFor` names which address holds a parked balance.
- Solana chain time is read from the Clock sysvar account. A transaction carrying an advance approval costs two signature fees.
- On Ethereum `SwapView.owed*` are zero unless read with `withOwed`, and are then account totals that can include other swaps.

### 7.10 The daemon as built

Additions and decisions made while building and while fixing the bugs the end-to-end suite found (`packages/daemon/DEVIATIONS.md`, `tests/e2e/BUGS.md`).

**Configuration keys added** (all optional): `[solana].maker_owner`, `[ethereum].maker_owner` (public owner keys, so the daemon knows which maker it is), `[solana].subscriptions`, `[ethereum].from_block`, `[monero].own_node`, `[monero].sweep_max_fee`, `[offers].eth_pool_size` (64), `[liquidity].ladder_headroom_pct` (1.0), `[registration].contacts`, `[daemon].console_dir` (serves the built console from the API's origin), `[daemon].cors_origins`, per offer `without_ready` (`"claim"` or `"abort"`), per keyed price source `base_url`, and for the pool source `base_vault`, `quote_vault`, `quote` (the pool is priced from its two reserve token accounts; without them the cross-check stays off). `claim_delay_minutes = "auto"` counts a depth tier as in use when its threshold is at or below `max_xmr`. `capacity_xmr` is capped at the largest unlocked output.

**Intents and stuck transactions.** `planned` (written before the action) → `sent` (written with the transaction id after signing and before the bytes leave) → `confirmed` or `failed`. A `planned` row found after a crash was never signed: it is failed and re-planned from finalized state. A `sent` row is looked up: found is confirmed; a dead blockhash or consumed nonce is failed and re-planned; otherwise the swap waits. After 5 minutes (Solana) or 1 hour (Ethereum) unresolved it is parked `needs_review` with a critical alert, is never re-sent, and keeps being looked up so a late landing is picked up. Transfers to third parties found unresolved at start are parked and never re-sent. Transactions that belong to no swap (rotation, registry, pause, messages) are looked up every minute and failed with an alert if they did not land. The Ethereum operator's sends are serialised (two could otherwise sign one nonce); a byte-identical Solana transaction on the same blockhash is refused before it is recorded.

**Monero inputs are exclusive.** Every wallet output is kept frozen in wallet-rpc. Every build (lock, split, payment) runs a freeze pass, reserves its inputs in the database before the wallet is asked, thaws only those, and refuses a result whose inputs are not exactly the reserved ones (dropped unstored and unrelayed; after three tries nothing is built). Reservations last until the wallet reports the output spent and survive restarts and reorgs. A relay the nodes refuse is journaled `failed`; only "accepted" or "already held" is `confirmed`. **Before the notice** the stored lock's inputs must be unspent in the chain and the pool on the nodes asked and reserved for that swap alone; otherwise the lock is discarded and rebuilt from another output, and if the nodes cannot be asked the notice waits. (The order of section 7.5 stands: the transaction is shown to a node only after the notice is final.) The lock and the sweep are each built once, stored, and re-published from the stored bytes.

**Operator instructions.** An instruction (`approve`, `reject`, `abort`, `withhold`, `release`, `publish-evidence`) is written to the swap's row inside the swap's own serialised section before anything acts on it, so a pass already running finishes first and a restart honours it. It is one-shot, counts as carried out only when its transaction is confirmed, and is otherwise planned again. A pass may refuse it only after reading the chain with the instruction on record. Exposure limits, paying caps and unlocked outputs count a swap from the moment it is approved. While paused, a stored automatic approval is not acted on; an explicit one by the operator is. On Ethereum the operator cannot pause on-chain (`setPaused` is the owner's): the switch stops quoting, rejects new locks and bumps the epochs.

**Ethereum key pool.** Generated in the background, one proof (about 0.2 s) per turn of the event loop, persisted as it goes; quoting continues on the current pool until its replacement is complete.

**Other.** `[approvals].advance` entries are honoured when the taker asks, not issued ahead. Quotes on request use the offer limits and at most the largest unlocked output, and are answered only over the maker endpoint. The inbox reads Solana, Tor and Ethereum events but never posts through the Ethereum contract. A parked payout raises an alert; the daemon builds the unsigned withdrawal for the owner to sign. Opposite-side flow is an alert only, and the measured refill cost is exposed but not fed into the deviation automatically (follow-up). `tor.reachable` is always `null`: the daemon runs no Tor client.

**Local API beyond the table of 7.8.** The WebSocket takes the token as `?token=` or a header. Swap actions answer 200 with `outcome: "carried_out" | "refused" | "pending"`, `refused: <reason>` (the SDK's reasons plus `not-available-in-state` and `dry-run`) and a `detail` sentence; `GET /api/swaps/:ref` carries `instruction`. New routes: `PUT /api/registration/published`, `GET /api/registration/links`, `POST /api/alerts/:id/ack`, `POST /api/rebalance/ack/:id`, `POST /api/swaps/:ref/withdraw-owed-tx`. `status.chains[]` carries the upgrade status of each deployment read from chain state (`upgradable`, `immutable` or `unknown`, the authority, a pending ownership transfer). A refused configuration carries `issues` and `warnings`. In dry run, actions that would send are refused with `409 dry_run`; pause works. There is no route to redeem held wXMR (declined until the bridge adapter is checked against the real program).

Tests: `pnpm --filter @xmrswap/daemon test` (unit, on the SDK's fakes, including the crash matrix) and `test:integration` (four full swaps against `svm-rpc`, anvil and regtest).

### 8.4 Recovery file

One file covers every swap, because every per-swap secret is derived from the seed and the swap's on-chain nonce.

```json
{ "format": "xmrswap-recovery/1", "created_at": "2026-11-21T12:00:00Z",
  "seed": "<64 hex>",
  "wallets": { "solana": ["<address>"], "ethereum": ["<address>"] },
  "program_id": "<Solana program id>", "contract": "<Ethereum contract address>" }
```

- Created and downloaded before the first lock; the lock button stays disabled until the user has saved it (download completed and a checkbox confirming it). Optionally passphrase-encrypted (`"seed_enc"`: scrypt + XChaCha20-Poly1305).
- Resume after a reload: list the wallet's swaps from chain state (Solana: `memcmp` on `taker`, the nonce is in the account; Ethereum: `swapsOf(taker, …)` then `getSwap`, which returns `swapNonce`; logs are only an index), re-derive each swap's keys from the seed and its nonce, decrypt the notice with the `maker_enc_key` stored in the swap, and continue.
- Escape hatch: for any swap whose two spend shares are known, "Export keys" writes address, private view key, private spend key, lock txid and height, which restore in standard Monero wallet software.
- Deriving the seed from a wallet signature (DESIGN's alternative) is **not offered in this version**: any site that obtained the same signature would hold every spend share and session key. The recovery file is the only backup.

### 8.5 Mandatory warnings

### 8.6 Large-swap router and leg states

Order entry: paying asset, total amount, destination XMR address, worst acceptable rate, maximum in-flight exposure, deadline. The router:

1. Reads every live offer for the market; drops offers that fail the taker's filters (depth below the depth required for the **total** in flight, approval window over the user's limit, maker fault or withhold rate over the user's limit).
2. Fills greedily from the best effective rate, `price × (1 + dep_bps × the maker's withhold rate)`, where a maker with no history counts as withhold rate 1, respecting each offer's `max_xmr` and `capacity_xmr` and never more than one leg per maker per wave.
3. Stops at the worst acceptable rate. Shows the plan: legs, blended rate against a reference, expected duration (for display: the approval window if pending, plus (depth + 1) × 120 s per wave), unfilled remainder. This is `planRoute` in the SDK; the UI does not re-implement it. The taker can edit legs.
4. Opens each wave with batched `lock` instructions (section 4.10: two SOL legs per Solana transaction, one USDC leg, or two with the lookup-table optimisation; one transaction per leg on Ethereum). New waves open as legs settle, within the in-flight cap.
5. If a maker stalls, refunds that leg under the normal rules and re-plans the remainder. The final report lists filled and unfilled amounts.

| Leg state | On-chain state | The tool |
| --- | --- | --- |
| Planned | none | Waits for the taker to approve the plan |
| Pending approval | PENDING | Waits; cancels or cranks the expiry |
| Locked | ACTIVE | Watches for the notice |
| XMR seen | NOTICED | Verifies the lock, shows confirmations against the depth |
| Ready | READY | Waits for the claim; refunds after `T_cd` if it does not come |
| Claimed | DONE with a revealed maker share | Computes the joint spend key |
| Swept | DONE; sweep confirmed | Closes the swap account |
| Refunded | HOLD, WITHHELD or DONE after a refund | Re-plans; tracks the deposit |

Each leg is an ordinary swap with its own nonce, keys and joint address; a failed leg never affects another.

The order itself (plan, remainder, worst rate, destination address, deadline) is not on-chain. It is stored in IndexedDB, encrypted like the seed. After a reload without it the legs still resume from chain state and the remainder is reported unfilled. The order's deadline means: no new wave is opened after it. "Depth required for the total in flight" is a constant table in `@xmrswap/protocol` (`TAKER_DEPTH_TIERS`: 2 below 1 XMR, 10 below 50 XMR, 25 from 50 XMR, applied to the sum of all open legs), which the user can raise.

### 8.7 Monero verification, sweep and connection modes

- Monero nodes are a user setting with no default: two or more independent nodes, or one marked "my own node". The UI runs `verifyLock` against all of them, fails closed on disagreement, takes depth as the minimum, and keeps polling until its sweep is confirmed.
- The sweep runs in the page through core-wasm against the user's most trusted node, with the fee cap. Before 10 confirmations the UI shows "yours, spendable in N blocks".
- An HTTPS page cannot call an `http://` node other than localhost; the self-hosted bundle ships the allow-listed proxy for that.

| Mode | Relay run by | Learns the user's IP | Notes |
| --- | --- | --- | --- |
| Hosted | The site operator | The site operator | Default |
| Self-hosted | The user | Nobody on the relay side | First-class path, section 8.8 |
| Tor Browser, direct | None | Nobody | Calls onion endpoints directly; untested |
| On-chain only | None | The RPC provider | Solana swaps only; Ethereum swaps need a blob route (section 6.4) |

### 8.8 Self-hosting

`deploy/` holds two equivalent one-command starts, both bound to localhost: `pnpm --filter @xmrswap/deploy start` (a static file server for the web UI on `127.0.0.1:8780` and the relay; needs only Node; it **does not start Tor**: it probes the configured SOCKS port and prints how to start a client if nothing answers), and a compose file for people who use containers. Acceptance uses the first; Docker is never required to build or test anything. The UI and the relay are served from **one origin** (the static server proxies `/relay/` and `/monero/` to the relay), because the relay sends no CORS headers by default; a deployment that separates them sets the relay's `allowed_origins`. The relay's `program_id` has no default and must be set to the release's id. And `docs/self-hosting/` covers: quick start; configuration reference (Solana RPC URL, Ethereum RPC URL, relay URL, Monero nodes, Tor proxy `127.0.0.1:9050`, relay bind `127.0.0.1`, pinned program id and contract address); safe defaults and a separate page on exposing the relay publicly with the rules of section 6.5 as requirements; who sees what in each connection mode; verifying the download (checksums, and checking the program id against the published one); the status page; troubleshooting (Tor unreachable and the on-chain fallback, RPC rate limits and the `getProgramAccounts` requirement, a Monero node out of sync, `--rpc-access-control-origins` for people running their own node); backups and upgrades without losing an in-flight swap.

### 8.9 The console, the taker UI and the bundle as built

**Console.** The daemon is the judge of the configuration: the console's own schema is a second copy, so a key it does not know is never an error locally; it is kept untouched, listed under "Settings not editable here" with the daemon's verdict, and a save is blocked only by the daemon's validation. A save changes only the edited lines (comments and unknown keys stay byte for byte); a file with multi-line values or arrays of tables is written afresh and the save bar says so. Every operator action shows its outcome where it was given. Owner actions on Ethereum: common wallets refuse `eth_signTransaction`, so the console always offers a paste box for a transaction signed offline. "Withdraw parked payout" is offered on every swap page. A light theme follows the system setting. Tests are vitest (no Playwright); wallet signing was tested with fake wallets only.

**Taker UI.**

- Solana wallets are found through the **Wallet Standard only**; the vendor adapters of `@solana/wallet-adapter-wallets` are not imported (they pull in SDKs that fetch remote code or call third parties).
- Settings: the page reads deployment defaults from `config.json` beside `index.html`; the browser stores **only the keys the user changed**, so an updated bundle reaches returning browsers. A Monero node may be a path on the same site (`/monero/0`).
- The page decides only from `finalized` state. On Ethereum that means waiting 13 to 19 minutes after the maker funds before the pay address is shown when selling; the page reads the newest block for display only, says what it is waiting for and which deadline runs meanwhile, and states the wait before any Ethereum swap.
- The maker's proof for a funded share is fetched and verified once, in the background, with retries, and cached; a proof that fails says "Do not send XMR".
- A confirmed request to get out always ends in a visible result: carried out, or refused with the reason and what happens instead; a control that would be refused is disabled and relabelled.
- The background loop never opens a wallet prompt by itself. After a refund the session key is swept, so collecting a held deposit later is a button ("Your deposit can be collected now"); anyone may also send that call.
- No price feed is fetched: the reference rate is the user's own figures from Settings, else the median of listed offers, labelled as such. Offers are ranked within one market by the maker's volume in that asset.
- Orders and inbox threads are sealed with AES-256-GCM under a seed-derived key. Advance approvals are requested from the page on Solana only. USDC legs of a large swap open one per transaction.
- Content-Security-Policy: `default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self'; connect-src http: https:` (the endpoints are user settings).
- Ethereum flows were first run in a browser by the end-to-end suite, not by this package's own browser tests (which cover Solana).

**Self-hosting bundle.** One settings file, `deploy/xmrswap.toml`, with `[ui]` and `[relay]` (the relay's own keys and `RELAY_*` overrides). `config.json` is generated per request. The UI server answers only requests whose `Host` is its listen address or the configured public origin (DNS-rebinding guard), and counts as one proxy hop in front of the relay. **The bundle raises the relay's rate limits to 6,000 requests and 1 GiB per minute**, because the page reaches its Monero nodes through the relay and the relay's own default (60 requests) cannot carry one swap's lock checks; a public relay must set them back. `run status` checks UI, relay, Tor proxy, RPCs, Monero nodes and the pinned program id. A release is a directory with `SHA256SUMS` made by `run release` and checked by `scripts/verify.mjs`; there is no archive, no signature and no publication channel yet. The compose file and Dockerfiles are validated as YAML against the bundle's own schema and **have never been built or run**. The pinned program id is the development id and the contract address is unset: nothing is deployed.

LiteSVM setup for every Solana test (from the research; each item was hit in practice): `LiteSVM::new()` (mainnet feature set); set the Rent sysvar to 5,080 lamports per byte; set the clock (`unix_timestamp` starts at 0 and `warp_to_slot` does not move it); a fresh blockhash per transaction (`expire_blockhash`), or a byte-identical retry is rejected (raw LiteSVM only; `svm-rpc` keeps a blockhash valid for 150 block heights as a cluster does, so two parties can fetch and then both send); failed transactions still charge the fee payer; assert CU as ranges. Funding is `svm.airdrop()`, which is in-process only.

Ethereum tests never fork a live network. A mock USDC (6 decimals, blacklist, pause) stands in for the token.

### 9.2 `tools/svm-rpc`: Solana for TypeScript tests without a validator

There is no local validator and none may be used. The daemon, SDK and web UI speak JSON-RPC, so the harness needs an endpoint. `svm-rpc` is a small Rust binary holding **one in-memory LiteSVM 0.16.0** and serving a JSON-RPC subset over HTTP on `127.0.0.1`. It is a test fixture, not a validator: no ledger, no consensus, no networking beyond loopback, and all state dies with the process. It reports a fixed fake genesis hash, so nothing configured for mainnet will accept it by mistake.

| Group | Methods |
| --- | --- |
| Standard (every commitment level is treated as final) | `getAccountInfo`, `getMultipleAccounts`, `getProgramAccounts` (`memcmp`, `dataSize`, `dataSlice`), `getBalance`, `getTokenAccountBalance`, `getTokenAccountsByOwner`, `getLatestBlockhash`, `isBlockhashValid`, `getMinimumBalanceForRentExemption`, `getFeeForMessage`, `getRecentPrioritizationFees`, `sendTransaction`, `simulateTransaction`, `getSignatureStatuses`, `getSignaturesForAddress`, `getTransaction`, `getSlot`, `getBlockHeight`, `getBlockTime`, `getEpochInfo`, `getGenesisHash`, `getVersion` |
| Control | `svm_addProgram(programId, soPath)`, `svm_setUpgradeAuthority(programId, authority)`, `svm_airdrop(pubkey, lamports)`, `svm_warp(seconds)` (moves `unix_timestamp` and the slot together and expires the blockhash), `svm_setClock(unixTimestamp)`, `svm_createMint(decimals, authority)`, `svm_mintTo(mint, owner, amount)`, `svm_setTokenAccountFrozen(tokenAccount, frozen)`, `svm_setAccount(pubkey, account)`, `svm_createLookupTable(addresses)` |

As built: the package exports `startSvmRpc({ programs })` (returns `url` and the control methods; builds the binary if missing), `sendAndConfirm`, `confirmSignature`, and a browser-safe `SvmRpcClient`. It also serves `getHealth`; `svm_createMint` takes an optional mint address and `svm_createLookupTable` an optional authority. The bind address is fixed to `127.0.0.1`; requests with a non-loopback `Host` or `Origin` get 403, and loopback origins get CORS headers. A landed transaction advances the slot by one; nothing else moves it except `svm_warp` (which also invalidates earlier blockhashes) and `svm_setClock`. `svm_airdrop`, `svm_createMint` and `svm_mintTo` write state directly and leave no signature. Transactions over 1,232 bytes are refused.

Differences from a real node that callers must allow for: **no WebSocket**, so web3.js `confirmTransaction`, `sendAndConfirmTransaction`, Anchor's `sendAndConfirm` and the `@solana/spl-token` action helpers hang (send raw and poll; use spl-token's instruction builders); slots do not advance with time (call `svm_warp`); everything is final at once; `jsonParsed` only for token accounts and mints, and no `getParsedTransaction`; `getBlock` and friends are absent; results of `getProgramAccounts` come back sorted.

It keeps an index of signatures per account so `getSignaturesForAddress` and `getTransaction` (with logs) work for message reading. It has no WebSocket; the SDK's Solana client takes `subscriptions: false` and polls, which is also its catch-up path in production.

If the owner rules that even this facade is too close to "a local validator", the fallback is the `litesvm` npm package in-process behind the SDK's `SolanaTransport` interface. That path was not run here and cannot serve the browser tests.

### 9.3 End-to-end harness (`tests/e2e`)

Global setup starts, on loopback only:

1. `svm-rpc` with the built program, `initialize`, a USDC mock mint.
2. `anvil` (chain id 31337, `--slots-in-an-epoch 1 --block-time 1`, so `finalized` is two blocks behind the head) with the contract deployed behind its proxy by `DeployAnvil.s.sol`, and the USDC mock. Where a scenario needs a realistic finality delay the daemon or the page reads Ethereum through a JSON-RPC proxy that holds `finalized`/`safe` back.
3. The Monero regtest (`tests/monero-regtest/start.sh --fresh`: two nodes and a wallet-rpc).
4. The real daemon as its own process in `live` mode against those three (registered through its own API with an owner key held outside it); the real relay process behind a fake SOCKS5 server that maps each maker's test onion name to its endpoint; the built taker UI and console in Chromium. Price sources are a loopback stand-in; venues and the rebalancer are not exercised here.

Time is driven explicitly: `advance(seconds)` calls `svm_warp` and `evm_increaseTime` + `evm_mine`; `mine(n)` mines Monero blocks. No test sleeps to reach a deadline. Teardown always runs `stop.sh`.

The taker side runs twice: headless through the SDK (every scenario) and in Chromium through `apps/web` with injected test wallets (scenarios marked UI).

## Open risks

Unverified or not run here:

- **The cross-curve DLEQ proof has no independent audit** (`sigma_fun` 0.9.0), and the two-address commitment (`keyAddr2`) is this project's own construction. Both are on the audit list. `curve25519-dalek-ng` sees little maintenance.
- Closed by M1: the Ed25519-precompile path, EIP-712 fixed-size arrays (Rust, viem, `cast` and Solidity agree byte for byte), the `wasm-bindgen` + `getrandom/js` build in Node 22 and Chromium, the nodejs wasm target, a viem signing round trip, the IDL generated from the skeleton, and the transaction byte counts (now measured). The Schnorr proof of knowledge, the envelope scheme and pay-or-park are implemented and tested against the vectors; none is audited.
- Closed since M1: the SDK runs against the built program, contract and regtest; the model is one implementation behind wasm; both contracts replay their vectors with no special cases; storage is packed; the session budget is measured; a real duplicate one-time key is produced on regtest; the v0 lookup-table transaction runs in `svm-rpc`.
- **End-to-end gaps** (section 9.5): oversized quotes, a dishonest maker on Ethereum, a fork-replaced lock, X-2 at depth 10, and several console actions in a browser were not run at system level. The rebalancer and every venue adapter are outside the end-to-end suite.
- **Nothing has touched a live network**: no devnet, Sepolia or mainnet deployment, no real Tor (the suite uses a fake SOCKS server), no real venue API, no stagenet or mainnet Monero, no real browser-wallet extension.
- The linked-library split puts settlement logic behind DELEGATECALL; that and the gas-starved-push case of section 5.4 belong on the audit list. The storage layout is now frozen by `ethereum/STORAGE.md` and must not change after a deployment.

- The browser sweep was run only in Chromium and only on regtest.
- The wXMR bridge IDL is outside this repository and has not been supplied; the adapter runs on documented assumptions.

Inherent in the design:

- **Closed tab.** A taker paying SOL, ETH or USDC whose tab is closed between `T_cut` and `T_co` loses everything to a maker that posted a false notice. Warnings and the automatic refund reduce this; nothing removes it.
- **Maker downtime in direction B.** A daemon that is offline through `[T_cut, T_co − M]` of a funded swap (roughly 45 minutes) can lose the escrow to a false notice.
- **Shallow depth.** Multi-block Monero reorgs have happened. Depth 2 protects only against one-block races; whoever relied on the lock carries the loss.
- **Browser compromise.** A compromised page holds the session key and the spend share; with a colluding maker it can set ready early and lose the funds. Self-hosting and a strict CSP are the mitigations.
- **Operator-key theft** exposes the maker's direction-B paying balance; keep it capped.
- **Withhold griefing.** A maker can post a false notice, wait for the refund and withhold: the taker loses up to 5% (half after the split), the maker gains nothing but pays only in reputation. The treasury's gain from unreleased deposits is a conflict of interest (sign-off item 8).
- **USDC freeze.** A freeze of the escrow or a pause of the token strands USDC legs; atomicity is lost. Disclosed in the UI.
- **Late secrets.** A secret-bearing transaction that lands after its window hands the counterparty both keys. Rule 2's margins are client discipline, not contract enforcement; a stuck Ethereum transaction near a boundary is the remaining exposure.
- **Finality stalls and chain halts.** An Ethereum finality stall makes an honest maker miss the notice deadline and is recorded as a fault; a long halt can consume a refund window.
- **Ethereum liveness of proofs.** Ethereum swaps need the maker's blob endpoint; without it nothing can be locked (no funds at risk, but no fallback).
- **Pending-slot exhaustion.** Filling a maker's 64 pending slots costs an attacker only transaction fees per attempt; the daemon's immediate rejection limits it to a fee war the attacker loses, but does not prevent it.
- **Counter gaming.** Fee-free refunds let a maker inflate some denominators by trading with itself, and the no-fault rejection reason is self-declared; the UI shows absolute counts and figures relative to completed swaps to blunt both.
- **Hosted defaults.** A dishonest set of Monero nodes or a dishonest RPC can fake a lock or serve a stale offer; several independent nodes, `min_seq` and self-hosting are the mitigations.
- **Maker privacy.** Address, volume and timing are public on the Solana and Ethereum side, and on-chain messaging reveals who messaged whom.
- **Upgrade key.** Until the contracts are frozen, users trust the project owner not to change the rules. Both UIs display the status.
