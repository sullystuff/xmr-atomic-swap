# WP5 (SDK) deviations from `docs/SPEC.md`

Recorded while building the unit part (milestone M1). Same vocabulary as
`docs/research/wp1-deviations.md`: **Deviation** = what was built differs from the text;
**Choice** = the text was silent or ambiguous and the smallest sound reading was taken;
**Note** = built as written, but the next package needs to know; **Request** = an interface
change this package would like from WP1 (nothing under `interfaces/`, `packages/protocol` or
`packages/core-wasm` was edited; the SDK builds to what is frozen).

Where the specification and a frozen artifact disagree, the artifact was followed: WP1's C7
(the Ethereum `quote_response` carries the compact form), E1 (`viewShare`), S1 (`Evidence`
struct), C15 (no `both` rows) and M1 to M12 (model conventions) are all taken as frozen.

## Found against the frozen interfaces

| # | Spec | Kind | What was done | Why |
| --- | --- | --- | --- | --- |
| D1 | 4.10 table: "`lock`, USDC, against a `Quote` account: 15 account keys, 875 bytes" | Deviation | The transaction the SDK builds has **14 keys and 843 bytes**; the size test asserts that. Every other row of the table is reproduced exactly (683, 811, 1,054, 1,182, 1,084, "does not fit", 1,156 for v0, 691, 1,097, 1,078, 1,201; `take` is 33 bytes smaller than `lock`). | 4.4 and the frozen IDL say exactly one of `offer` and `quote` is present, so against a quote the offer key drops out: 13 − 1 + 2 = 14. The table's figure counts the offer as well. The real transaction is 32 bytes smaller, so nothing that depended on it fitting changes. |
| D2 | 2.12 frozen wasm list; 3.1 "price of the highest used tier with xmr >= tier threshold; depth likewise" | Request | The tier lookup is implemented in the SDK (`tierValue`, `src/registry/pricing.ts`) and tested against the fourteen `tier` cases of `amounts.json`, including the five `TiersInvalid` ones. | `@xmrswap/core-wasm` exports `payAmount`, `receiveAmount`, `depositOf`, `feeOf` but no tier function, and a client cannot price a size without one. Request: export `tierValue(above, values, xmr)`; the SDK then drops its copy. |
| D3 | 2.12 "the reference model … `apply`"; 10.2 "taker flows and maker flows as pure state-driven functions"; task: "deadline computation identical to the reference model" | Request | The state machine is ported to TypeScript (`src/machine/model.ts`, a line-for-line port of `swap_core::model::apply`). Bounds, `Δ_cut` inputs, deposit, fee and split still come from the core. The port is held to the model by replaying **every** row (798) and sequence (364) of `transitions.json`, per chain, with payouts, counters, `t_*` fields and the maker record. | The wasm API exports `deadlines` but not `apply` or `enabled`, and the flows must know, for any state and second, which calls the contracts accept. Request: export the model through wasm; the SDK would then call it instead. |
| D4 | 2 "TypeScript MUST NOT re-implement anything here except the pure-JS Monero transaction scan" | Choice | Three things use `@noble/*` directly rather than the core, because the frozen wasm API has no export for them: Ed25519 sign/verify of the 190-byte advance approval (`signSolApproval`, `solApprovalProblem`; verification is strict, `zip215: false`, the precompile's rule); Ed25519 signing of Solana transactions with a derived session or operator seed (`seedSigner`); SHA-256 of an envelope for `in_reply_to`. EIP-712 signing and recovery are viem's, as 2.10 says, with the digest cross-checked against the core's `quoteDigest` / `approvalDigest` on every call. | These are library calls on standard primitives, not re-derivations of this protocol's constructions; the bytes that are signed still come from the core (`encodeSolApproval`). Vectors: every `sol_signed.json` case, signature bytes included. |
| D5 | 2.11 "lift `lib/monero.mjs`, `lib/verify.mjs`, `lib/watch.mjs`" | Deviation | Lifted: transaction parsing, txid recomputation, view-key scan, `verifyLock`, block output keys, duplicate detection, `findDeposits`. **Not** lifted: the key-half, joint-key, base58 and address code of `lib/monero.mjs`. | That code re-implements 2.2 and 2.5, which the same section forbids in TypeScript; the SDK calls `jointAddress`, `addScalars` and `scalarMatches` of the core instead (`src/flows/keys.ts`). |
| D6 | 2.11 `verifyLock({ nodes, txid, viewPriv, spendPub, minAmount, minConf, minNodes })` returns `{ ok, state, reasons, amount, confirmations }` | Choice | Arguments: plus `ownNode` (the user's declaration for a single node). A list of one node without it, an empty list, or `minNodes` below the list length throws `NodePolicy`. Result: plus `codes` (stable reason codes; each `reasons` string starts with its code), `outputIndex`, `blockHeight`, `outputs`, `nodes`. Nodes are URLs or `MoneroNode` objects (the seam tests use). | "`minNodes` = the list length" and "fail closed" leave no meaning for a smaller value; `outputIndex` is what WP1's C9 says the sweep needs. |
| D7 | 2.7 / `merkle.json` cases `*-proof-for-another-leaf`, `*-tampered-proof` | Note | Not consumed. The SDK never verifies somebody else's Merkle proof: it accepts a pool only if its leaves hash to the signed `keyRoot` and then builds its own proof with the core. A swapped, re-indexed or missing leaf is tested as a root mismatch. | The frozen wasm API has no proof verifier and writing one would re-implement 2.7. |
| D8 | `terms.json` case `extremes` (`fee_bps` 65535) | Note | Skipped in the SDK's test of `offerTermsHash`; the other six cases are checked. | An offer has no fee field; the SDK hashes with `FEE_BPS`, as the program does. The case is covered by `@xmrswap/core-wasm`'s own test. |
| D9 | 5.2 `owed[token][account]`; 4.2 `owed_taker`, `owed_maker`, `owed_treasury` | Note | `SwapView.owedTaker/owedMaker/owedTreasury` are per swap on Solana. On Ethereum they are zero unless `getSwap(…, withOwed = true)`, which reads `owedOf(token, account)`: an account-level total that can include other swaps. | The contract parks per account, not per swap. |
| D10 | 5.2 `bytes32` fields, `uint256 revealed` | Note | Assumed, and what the vectors show: every `bytes32` (spend commitments, view shares, encryption keys, txid) holds the same 32 bytes as on Solana; `revealed` and the `secret` argument are the share as an integer (`secret_uint256` of `twin.json`), converted to and from the 32 little-endian bytes Monero uses. | WP3 should confirm at integration. |

## Choices in the flows (SPEC 3.11, 7.5 leave them open)

| # | Spec | Kind | What was done | Why |
| --- | --- | --- | --- | --- |
| F1 | 3.11 taker (4) "at depth before `T_cut` call `set_ready`, at `T_cut` otherwise call `refund`" | Choice | If the lock is confirmed at depth after `T_cut` but the refund has not been sent yet (a tab that came back late), the flow sets ready (allowed until `T_co`) instead of refunding. Otherwise as written: refund from `T_cut`, never after `T_co − M`. | Both parties are better off, and the risk is the same as setting ready before `T_cut`. |
| F2 | 3.2 rule 2 | Choice | A secret-bearing call is proposed only while it stays acceptable for `M − 1` more seconds: taker refund until `T_co − M` (NOTICED) or `T_final − M`; maker claim until `T_cd − M` (READY) or `T_exp − M`; direction-B taker claim until `T_cd − M` (READY) or `T_exp − M` (the two claim windows `[T_co, T_final)` and `[T_final, T_exp)` are one continuous window); maker refund until `T_co − M` / `T_final − M`. Refunds in ACTIVE have no limit (valid at every instant). A unit test checks all of this against the model for every state in `transitions.json`. | The text names the boundaries; this is the arithmetic. |
| F3 | 3.4 A8 versus A10g | Choice | After `T_note` with no notice the taker's flow sends the keyless `refund_unnoticed`, not the keyed refund. | Same funds, no secret published. |
| F4 | 7.5 direction A step 5 | Choice | The maker relays its prepared lock only before `T_cut`; later it aborts. With no ready at `T_co` the default is: claim if its own lock verifies as confirmed, otherwise abort (`withoutReady` overrides). | After `T_cut` the taker's tab refunds by itself, so a late relay only burns fees. |
| F5 | 3.5 B9b | Choice | With no notice at `T_note` the maker's flow refunds at once (it is valid in ACTIVE and, if a late notice lands first, in NOTICED). | The escrow is the maker's capital; the text only says the refund exists. |
| F6 | 4.5 `close_swap` | Note | The flows propose `close_swap` (Solana) once the caller has swept and nothing is owed: the taker after a claim in A, the operator after a refund in A or a claim in B. It is the one proposed call the model does not know. | |
| F7 | 5.6 "clients keep history attached to both keys after an unlink" | Choice | `LinkMemory`: a client-side set of pairs that were ever seen mutually linked; `mergedReputation` keeps merging for a remembered pair. A reader with no memory sees only current state. | Current chain state alone cannot show a past link; the alternative is replaying `LinkChanged` events, which is a later addition. |
| F8 | 8.6 router | Choice | Effective rate = price × (1 + `dep_bps` × withhold rate); a maker with no history counts as withhold rate 1. The depth requirement is applied to each wave's total XMR and the wave is re-planned without the offers that fail it. Expected duration is `W_a` (if pending) + (depth + 1) × 120 s per wave, for display only. | "Price plus expected deposit cost" is not defined further. |
| F9 | 5.4 "sizes the budget for four calls at a capped gas price" | Choice | `ethSessionBudget(maxFeePerGas, gasPerCall = 150,000, calls = 4)`. The per-call gas is a placeholder until measured against WP3's contract. | |

## What the integration part will need

- **WP4 (`svm-rpc`)**: the CLI of its `main.rs` (`--port 0`, `--program <id>=<so>`, `--unix-timestamp`, the "listening on" line). The `SolanaTransport` over web3.js uses: `getAccountInfo` (including the Clock sysvar, which is where the SDK reads chain time), `getMultipleAccounts`, `getProgramAccounts` with `memcmp`, `getLatestBlockhash`, `getMinimumBalanceForRentExemption`, `getGenesisHash`, `simulateTransaction` (base64, `sigVerify: false`, `replaceRecentBlockhash: true`, `unitsConsumed` in the result), `sendTransaction` with preflight, `getSignatureStatuses`, `getSignaturesForAddress` (`until`), `getTransaction` (logs, `maxSupportedTransactionVersion: 0`); and the control methods `svm_warp`, `svm_setClock`, `svm_airdrop`, `svm_setUpgradeAuthority`, `svm_createMint`, `svm_mintTo`, `svm_setTokenAccountFrozen`, `svm_createLookupTable`.
- **WP2 (program)**: the built `solana/program/target/deploy/xmr_swap.so`; Anchor custom error codes as in the IDL (the client maps `{ Custom: 6000 + n }` to names); events through `emit!`; "closed" rows closing the swap account (the watcher reports the account disappearing).
- **WP3 (contract)**: `ethereum/out/XmrSwap.sol/XmrSwap.json` and the proxy artifact; custom errors as revert data on `eth_call` and `eth_estimateGas`; confirmation of D10; its decision on WP1's E4 (how `setPaused`, `bumpEpochs`, `cancelQuote`, `revokeApproval` find the maker for an operator caller).
- **Regtest**: `tests/monero-regtest` running (`XMR_BIN`), for `verifyLock`, `findDeposits` and `sweepJoint` against two real nodes, including a real duplicate one-time key (WP1's C13 is synthetic).
