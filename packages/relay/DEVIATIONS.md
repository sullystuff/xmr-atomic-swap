# WP6 (relay) deviations from `docs/SPEC.md`

Same format as `docs/research/wp1-deviations.md`. "Deviation" = differs from the text. "Choice" = the text was silent or ambiguous and the smallest sound reading was taken. "Note" = built as written, but the next package needs to know. "Request" = an interface change asked of WP1; the relay is built to what is frozen.

| # | Spec | Kind | What was done | Why |
| --- | --- | --- | --- | --- |
| R1 | 6.5 forward: "returns `{ status, body_b64 }`" | Choice | An upstream **3xx** is not relayed: the relay answers 502 `upstream_redirect` and never follows it. Every other upstream status (2xx, 4xx, 5xx) is passed back inside `{ status, body_b64 }` with HTTP 200. | DESIGN: never an open proxy. A browser client that received a `Location` could be steered off the registry. |
| R2 | 6.5 (error responses are not specified) | Choice / Request | Relay errors are `{ "error": code }`: 400 `bad_request`, `bad_onion`, `bad_path`; 403 `onion_not_listed`, `monero_path_not_allowed`, `monero_method_not_allowed`; 404 `not_found`, `no_such_node`; 405 `bad_method`; 413 `too_large`; 429 `rate_limited` (with `Retry-After`); 502 `upstream_unreachable`, `upstream_too_large`, `upstream_redirect`; 504 `upstream_timeout`. Request to WP1: add this shape and the code list to `@xmrswap/protocol` (`messages.ts`). | WP5 and WP10 need to tell "relay refused" from "maker refused". |
| R3 | 6.5 "`{ onion, method, path, body_b64? }`" | Choice | `body_b64` is required for `POST` and `PUT`, forbidden for `GET`, and must be strict padded base64. `onion` must be exactly 56 base32 characters + `.onion` (lower case, no port, no trailing dot) and is checked before the registry is consulted; whatever the registry source returns is filtered by the same rule. | No route takes an empty upload; lenient decoding would let the caps be argued about. |
| R4 | 6.5 "reads maker accounts … every 60 s and on a miss" | Choice | A miss triggers a re-read at most once per 5 s (concurrent lookups share one read). If reads keep failing, the last list is used for up to 10 minutes and then dropped (every forward refused). | Otherwise unlisted-onion requests become an RPC flood; and "currently in the registry" cannot be claimed of an hour-old list. |
| R5 | 6.5 status: `registry_age_secs`, `makers` | Choice | `registry_age_secs` is `-1` until the first successful read. `makers` counts all maker accounts, with or without an onion address. | The frozen type is `number`. |
| R6 | 6.5 status: `tor_ok` | Choice | `tor_ok` means the SOCKS5 proxy answered a method negotiation. No connection is opened through it, so it does not prove Tor has bootstrapped. Probe results (Tor and Monero heights) are reused for 5 s. | A check that builds a circuit needs a destination, and the relay must not pick one. |
| R7 | 6.5 "Per-IP limits (default 60 requests and 4 MB per minute)" | Choice | Fixed one-minute windows. Every request counts, including refused ones and status; `OPTIONS` preflights do not. Bytes counted: request bodies and relayed response bodies. A request is admitted while the budget is not yet used up, so one large response can overshoot it; the address is then refused until the window ends. 4 MB = 4 × 1024 × 1024, as in `RELAY_LIMITS`. | |
| R8 | 6.5 settings | Choice | Added settings not in the list: `allowed_origins` (CORS; default none), `trust_proxy_hops` (default 0), `monero_max_response_bytes` (default 16 MiB), `debug_log` (the "debug flag"). The Solana RPC URL is read from the environment variable named by `solana_rpc_url_env` (default `SOLANA_RPC_URL`). `program_id` has **no default**. All keys, defaults and environment names are in `relay.example.toml`. | A hosted relay sits behind a reverse proxy (per-IP limits need the hop count). `@xmrswap/protocol` exports no pinned program id; request to WP1/WP12: provide the release's id. |
| R9 | 6.5 (CORS is not mentioned) | Note | By default the relay sends no CORS headers. WP10/WP12: when the UI is served from another origin (another port counts), set `RELAY_ALLOWED_ORIGINS` to that origin, or put both behind one reverse proxy. | With `*` on a localhost relay any web page the user visits could use their relay and Monero nodes. |
| R10 | 6.5 "`POST /monero/<n>/<path>`: Raw body" | Choice | `POST` only; `n` counts from 0; the query string is never forwarded; the 96 kB request limit applies here too. For `/json_rpc` the body must be one JSON object (no batch) with an allow-listed `method`, and the relay forwards the **re-serialised** object, not the client's bytes. Only `Content-Type` and the body travel in either direction. A node redirect is refused (R1). A node URL is `http(s)://host[:port]` with no path or credentials; a `.onion` node is reached through the Tor proxy. | Re-serialising closes the duplicate-key trick (`{"method":"flush_txpool","method":"get_info"}`) against a node parser that keeps the first key. |
| R11 | 6.5 "No message logs by default … A debug flag enables logging" | Choice | Default output is the start line, configuration warnings and "registry refresh failed" without its reason (the reason can contain the RPC URL and its API key). Debug adds one metadata line per forwarded request (client IP, onion, path, sizes, status). Bodies are never logged at any level. | |
| R12 | 1.4 dependency table | Deviation | `smol-toml` 1.9.1 added to the relay (the table lists it for the daemon only). `ws` stays in `package.json` as WP1 wrote it but is unused. | `relay.toml` needs a parser; the daemon's is already in the workspace. |
| R13 | 10.1 package skeleton | Note | The package has a `prepare` script (`tsc`), like W10, so `dist/` exists after `pnpm install` and `@xmrswap/relay` can be imported (`startRelay`, `loadConfigFromProcess`) or run as `xmrswap-relay` / `pnpm --filter @xmrswap/relay start`. `test` type-checks sources and tests, then runs vitest. | WP12 starts the relay from `deploy/`. |
