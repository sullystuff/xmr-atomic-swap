# WP7 deviations from `docs/SPEC.md`

Recorded by work package 7 (`packages/rebalancer`). "Deviation" = differs from the text.
"Choice" = the text was silent or elided and the smallest sound reading was taken. "Request" =
an interface change asked of the architect or WP1; the package is built to what is frozen and
works without it. "Note" = built as written, but the next package needs to know.

## Interface (SPEC 7.7)

| # | Spec | Kind | What was done | Why |
| --- | --- | --- | --- | --- |
| R1 | `sendSol(...)`, `sendEth(...)`, `sendXmr(...)` (arguments elided) | Choice | `sendSol(SolSend)` where `SolSend` is a plain transfer (`sol` or `usdc_sol`), a list of unsigned instructions, or a base64 versioned transaction for the wallet to sign; `sendEth({ asset, to, amount })`; `sendXmr({ to, amount })`. Each resolves with the transaction id **after confirmation** and never re-sends. `now()` is Unix seconds. | The bridge needs program instructions and Jupiter's pre-built transaction signed by the maker's wallet; adapters hold no keys. WP8 implements exactly these three shapes. |
| R2 | `cancel?(handle)`, `resolveHeld?(handle, choice)`; no way to take a later step | Request | `cancel` and `resolveHeld` accept an optional trailing `ctx?: ExecContext`, and an optional `advance?(handle, ctx)` is added. The frozen one-argument `cancel(handle)` still works: the bridge adapter then uses the `execContext` given at construction, and fails with a clear message if there is none. | Cancelling a bridge redemption is a Solana transaction, which only `ExecContext` can send. The bridge's later pieces and reverse path, and the exchange's trade and withdrawal, happen after `execute` returns and must be journalled; `status` has no context to journal through. `Rebalancer.tick` calls `advance` when an adapter has it and `status` otherwise. |
| R3 | `RefillStatus` | Request | Optional `unfilled?: bigint`: input the venue did not use. | DESIGN: "split the order into smaller pieces … or pass the remainder to the next venue". Without it the router cannot know how much is left. |
| R4 | "Adapters hold no keys … All secrets stay in the daemon" | Note | Adapters read API credentials from the environment by variable name at call time (`api_key_env`, `api_secret_env`) through an injectable reader. Values are never stored, journalled or put in errors (errors carry method, URL without query, status and the venue's message only). | DESIGN's example names credentials by environment variable. If the daemon keeps them encrypted in its keystore instead, it passes its own `EnvReader`. |
| R5 | `VenueQuote.feesUsd`, `costPct` | Choice | `feesUsd` = value in minus value out at the reference price, plus network fees; `costPct` = that over the value in. It can be negative. | "Total cost against the reference price" is one number; the venue's spread is part of it. |
| R6 | Handles | Note | A handle is `venue:…`. FixedFloat's carries the order's access token and the refund address (needed for `/order` and `/emergency`); that token is not an API credential, but the daemon should treat handles as private. | FixedFloat takes no refund address at creation. |

## Adapters

| # | Spec | Kind | What was done | Why |
| --- | --- | --- | --- | --- |
| A1 | "the owner places the current IDL at `vendor/wxmr_bridge.json` … until then WP7 … marks its encoding tests pending" | Note | Not supplied. Encoders are built from `local-assets.md`; `BRIDGE-ASSUMPTIONS.md` lists every assumed layout; the IDL-conformance suite skips with a warning until the file exists; the golden-byte encoding tests run regardless. | As instructed. |
| A2 | `exchange`: "one concrete driver chosen by `name`" | Choice | The driver is **Kraken** (`name = "kraken"`). The driver interface has the five calls of the spec plus `depositCredited`, `estimate`, `orderStatus`, `withdrawFee`, `limits`, `needsTrade`, `ready`. Trades go through USD in two market orders. | Kraken lists XMR/USD and only withdraws to addresses registered under a key name, which is the allow-listing DESIGN asks for. The extra calls are what quoting and a restart-safe state machine need. Unverified against the live API (the request signature matches Kraken's published example). |
| A3 | `exchange`: withdrawal allow-listing | Choice | The Kraken driver refuses any payout address that has no entry in `withdrawKeys` (address to registered key name), passed in by the daemon; the settings schema has no key for it. | DESIGN's example has only `withdraw_address_allowlist = true`. A `[rebalance.venues.exchange.withdraw_keys]` table would be a schema addition for the architect. |
| A4 | `wxmr_bridge`: "a direct read of the pool for depth" | Choice | Depth is an injected `PoolDepthReader`; `vaultPoolDepth` reads the pool's two reserve token accounts, whose addresses are configuration. With no reader the adapter falls back to halving the piece until Jupiter's `priceImpactPct` is within `max_piece_pct_of_pool`. | The DLMM pool layout was not verified, and decoding it needs a dependency outside SPEC 1.4. |
| A5 | `wxmr_bridge`: reserve proof "verified with the maker's own Monero node" | Choice | An injected `ReserveProofVerifier` (wallet-rpc `check_reserve_proof`), which the daemon implements. With `reserve_proof_check_above_xmr` set and no verifier, refills above the size are refused. | This package has no Monero node access. |
| A6 | `wxmr_bridge` after a cancel | Note | A cancelled redemption returns wXMR, not USDC. The retry on the next venue spends new USDC; the wXMR stays in the wallet (bounded by `max_wxmr_held`, which also blocks further bridge buys) until `redeemHeld` is called. | That is what `cancel_withdrawal` does. |
| A7 | `wxmr_bridge` reverse path | Choice | Priced by `amountIn` or `amountOut`; pays out only to the maker wallet that owns the deposit record; cannot be cancelled once the XMR is sent. A piece whose price is above the cost limit is waited out, not passed on. | The wXMR is already held at that point. |
| A8 | `houdiniswap`, `stealthex` | Note | Implemented from the public descriptions, **disabled by default**, and enabling either prints a warning: XMR support is unconfirmed. HoudiniSwap's request and response fields are the least certain of the four. | SPEC "Open risks". |
| A9 | `fixedfloat` rate limit | Choice | The adapter keeps a local budget of 250 units a minute, `create` = 50, every other call = 1, and refuses a call that would pass it. | Only `create`'s weight is documented in the research. |
| A10 | Fixtures: "recorded-fixture tests" | Deviation | **All fixtures are hand-written** from the public docs; none is recorded. `test/fixtures/README.md` says so per file. | No API key may be used and no venue may be contacted. |

## Routing and safety rules

| # | Spec | Kind | What was done | Why |
| --- | --- | --- | --- | --- |
| S1 | 7.1: the daemon's `rebalance/` module holds "triggers, routing, modes and safety controls" | Choice | Routing, caps, modes, allow-list, test transfer, stall handling and the cost log live here in `Rebalancer`; the daemon keeps the triggers, the `ExecContext`, storage and the API. `evaluateLevels` is a pure helper for level triggers. | The WP7 brief: safety controls are enforced in this layer, not left to callers. |
| S2 | 7.2 `[rebalance.allowlist]` default: "the inventory wallet and the operator and payout addresses" | Note | The schema default is empty lists, and an empty list allows nothing. The daemon passes the default addresses as `allowlist`. Checked three times: by `Rebalancer` on every request and again immediately before execution, and by `guardAdapter` around every adapter `createAdapters` builds. | This package cannot know the maker's addresses. |
| S3 | `max_share_pct` (per venue) | Choice | A venue may carry at most that share of `routing.max_per_day_usd` in a rolling 24 hours; without a daily cap it has no effect (warned). Settable in `[rebalance.routing]` and per venue. | A share of volume already done would let the first refill of a day be 100%. |
| S4 | "every item is configurable per … venue" | Choice | Every venue section also accepts `max_cost_pct`, `max_per_tx_usd`, `max_per_day_usd`, `max_share_pct` and `mode`. A venue's `max_cost_pct` replaces the global one for that venue. | DESIGN's bridge section already sets its own `max_cost_pct`. |
| S5 | Caps | Choice | A refill larger than a cap is cut to the cap rather than refused; the daily cap counts refills when they start, over a rolling 24 hours. Unknown keys under `[rebalance]` are errors. | A misspelt cap must not mean "no cap". |
| S6 | `test_transfer_usd` | Choice | A venue/payout-address pair is "new" until a refill to it completes. The first transfer is `max(test_transfer_usd, venue minimum)` (or the whole refill if smaller); the rest follows on the same venue once it arrives, with no second approval in approve mode. | |
| S7 | "a failed venue cools down" / "retry on the next venue" | Choice | A venue that fails before sending anything cools down and the next venue is tried at once. A refunded or cancelled refill is retried on the next venue. A **failed** refill is retried too, but its value keeps counting against `max_in_transit_usd` until the maker acknowledges it. An ambiguous send (an error after the adapter handed something to the wallet) is parked as `held`, stays counted as in transit, and is never retried elsewhere; `acknowledge` closes it once the maker has checked. An error before any send is a clean failure whatever the adapter threw. A stalled refill that cannot be cancelled is tracked, not duplicated. | The same value must never be in two places, and the in-transit cap must bound the loss when a venue fails. |
| S8 | Defaults | Choice | `mode` defaults to `alert`; every venue defaults to `enabled = false`; `rate` defaults to `float`; `routing.choose` to `priority`. | SPEC 7.2 gives no defaults for these; the safe ones were taken. |
| S9 | `[rebalance.cross_chain]` | Note | A `usdc_sol`/`usdc_eth` pair is routed only to `cross_chain.venue`, under `cross_chain.max_per_tx_usd` and `max_cost_pct`, and only when enabled. The bridge is refused as that venue. | |
