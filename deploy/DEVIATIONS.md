# WP12 (self-hosting bundle and docs) deviations and hand-over notes

Same vocabulary as the other packages: **Deviation** = differs from the text; **Choice** = the text was silent or ambiguous and the smallest sound reading was taken; **Note** = built as written, but the next reader needs to know; **Request** = a change this package would like elsewhere. Nothing outside `deploy/` and `docs/self-hosting/` was edited.

## Running it

```sh
pnpm --filter @xmrswap/deploy start          # UI on 127.0.0.1:8780, relay on 127.0.0.1:8787; never starts Tor
pnpm --filter @xmrswap/deploy run status     # UI, relay, Tor proxy, Solana RPC, Monero nodes; exit 1 on a failure
pnpm --filter @xmrswap/deploy test           # acceptance: loopback fakes only
```

## Deviations and choices

| # | Spec | Kind | What was done | Why |
| --- | --- | --- | --- | --- |
| D1 | 8.8 "the relay, and the system `tor` if one is on the PATH"; DESIGN "one command that starts the UI, relay and Tor together" | Deviation | The Node start command does **not** start Tor. It probes the configured SOCKS port and, if nothing answers, prints how to start a Tor client or point at an existing one. Only the compose file brings its own Tor (a container). | The work order: the bundle must not start, stop or reconfigure a Tor client on the user's system. A start command that spawns a second `tor` beside a system service on port 9050 fails or fights it. |
| D2 | 8.8 "a single settings file" / 6.5 `relay.toml` | Choice | One file, `deploy/xmrswap.toml` (found in `deploy/` or through `XMRSWAP_SELFHOST_CONFIG`), with `[ui]` (bundle and page defaults) and `[relay]` (exactly the keys of `relay.toml`, handed to the relay's own `loadConfig`, so its validation and every `RELAY_*` override apply unchanged). `RELAY_CONFIG` is not read. `[ui]` keys: `listen`, `dist`, `public_origin`, `give_page_rpc_urls`, `ethereum_rpc_url_env`, `ethereum_chain_id`, `contract_address`, `monero_network`, `own_node`, `poll_ms`; each has an `XMRSWAP_UI_*` override. Unknown keys are errors. | One list (`SETTINGS` in `src/settings.ts`) generates the example file and the docs tables; tests hold it to the relay's `TOP_KEYS`/`RATE_KEYS`, its `RELAY_*` names, `relay.example.toml` and the page's `DEFAULT_SETTINGS`. |
| D3 | 6.5 "Per-IP limits (default 60 requests and 4 MB per minute)" | Deviation | In the bundle the default is 6000 requests and 1 GiB per minute. The docs say so wherever the limits appear, and the public-relay page requires setting them back. | The page reaches its Monero nodes through the relay. One lock check is three or more node calls per node every `pollMs` (4 s): two nodes exceed 60 a minute for a single swap, and the node responses a sweep needs can exceed 4 MiB (not measured here). With the relay's defaults a self-hosted page gets `429` from its own relay in the middle of a swap. (WP11's harness sets 100000 and 4 GB for the same reason.) |
| D4 | 6.5 `trust_proxy_hops` | Choice | The UI server is itself a proxy hop in front of the relay: it appends the caller's address to `X-Forwarded-For` and the bundle starts the relay with `trust_proxy_hops + 1`. The documented setting counts only proxies the operator adds. | Otherwise every client behind the UI server would share one budget (the relay would see only 127.0.0.1), and a public deployment could not limit per client. |
| D5 | 8.8 (not specified) | Choice | The UI server answers only requests whose `Host` is its listen address (`127.0.0.1`, `localhost`, `[::1]` with the port) or the host of `[ui] public_origin`; anything else gets `421 bad_host`. | DNS rebinding: a web site that resolves its own name to 127.0.0.1 would otherwise be same-origin with the bundle and could use the relay, the Monero nodes and read `config.json`. |
| D6 | apps/web hand-over: "WP12's bundle should write `config.json` (relay at `/`, Monero proxy nodes `/monero/0`, …)" | Choice | `config.json` is generated per request and never written into `apps/web/dist`. The Monero nodes are given as absolute URLs (`http://<Host>/monero/<n>`), built from the request's host or `public_origin`. | The page's `settingsProblems` accepts only `http(s)` URLs for Monero nodes; `/monero/0` is reported as "not an http(s) URL" and blocks locking. Not writing into another package's build output also keeps the UI directory equal to the checksummed release. |
| D7 | 8.8 "Solana RPC URL" setting; 1.5 secrets from the environment | Choice | The page's Solana and Ethereum RPC URLs come from the environment (`SOLANA_RPC_URL`, `ETHEREUM_RPC_URL`) and are put into `config.json` unless `[ui] give_page_rpc_urls = false`. The start command warns when the page is public and this is on. No command prints an RPC URL. | The page needs the URL; on loopback only local programs can read it (the docs say so). On a public page it would publish the operator's API key. |
| D8 | 8.8 "a static file server" | Note | Port 8780 for the UI (the specification names none). The server sends `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, same-origin resource and opener policies; it does not repeat the page's CSP as a header (the page carries it in a meta tag, and a second copy could drift). No request log. `GET`/`HEAD` only outside `/relay/` and `/monero/`. | |
| D9 | DESIGN "A status page showing Tor reachable, RPC connected and Monero nodes in agreement" | Choice | Two forms: the page's own Status page (WP10), and `run status`, which asks the same questions from Node: UI served, relay reachable and registry read, Tor proxy (the relay's `tor_ok`, labelled as a SOCKS handshake only), Solana RPC (`getGenesisHash`, and the pinned program must be an executable account), Ethereum RPC if set, Monero nodes through the bundle's own proxy, and the page's program id against the pinned one. The Monero rule is a copy of the page's `moneroAgreement`; a test compares the two case by case. | The CLI cannot test "maker reachable over Tor" without choosing a maker and speaking the SDK's protocol; the docs send the reader to the Status page for that. |
| D10 | 8.8 "a compose file ... validated only as YAML against a bundled schema" | Choice | `compose.schema.json` is this bundle's own schema: the subset of the Compose format the file uses, plus rules of its own (published ports must be `127.0.0.1:…`, named volumes only, no unknown keys). It is not the Compose Specification's schema. | The official schema could not be fetched in the build environment, and it would accept `0.0.0.0` ports and host mounts. **The compose file and both Dockerfiles have never been built or run.** |
| D11 | 8.8 "verifying the download (checksums ...)" | Choice | A release is a directory (`web/`, `release.json`, `SHA256SUMS`), made by `run release`; `scripts/verify.mjs` (no dependencies) fails on a changed, missing or unlisted file; the list is `sha256sum`-compatible. No archive and no signature are produced. | There is no project signing key or publication channel yet; the docs say that a checksum is only as good as where it came from. Reproducibility was observed only for the JS/CSS build on one machine with the same wasm; the Rust-to-wasm step was not compared across machines. |
| D12 | 10.3 WP12 acceptance | Note | The acceptance command also runs the built page's Status page in Chromium against the bundle (`test/browser.test.ts`), so it needs a Chromium (`$CHROMIUM` or the Playwright cache, as for WP10) and fails, not skips, without one. It needs the built UI: `scripts/ensure-ui.mjs` builds what is missing (which needs the wasm toolchain) and never rebuilds what exists. | "Checks the status page" is only real in a browser. |
| D13 | 1.4 dependency table | Deviation | Added to `deploy/package.json`: `@xmrswap/protocol`, `smol-toml` 1.9.1 (runtime); `yaml` 2.9.1, `ajv` 8.20.0, `playwright-core` 1.56.1, `@solana/web3.js` 1.98.4 (tests). `pnpm-lock.yaml` was not committed. | YAML and schema validation; the Status-page test; a real PDA and real account encodings in the fake Solana RPC. |
| D14 | 8.8 "pinned program id and contract address" | Note | `PROGRAM_ID` is still the development id and `CONTRACT_ADDRESS` is `null`. The docs say nothing is deployed and no published value exists to compare with. When the owner deploys, `verifying-the-download.md` needs the place the ids are published. | |
| D15 | Work order: "every command in the docs must be one you actually ran" | Note | Marked "Not run" in the docs: `rustup`/`cargo install`, `tor …`, the systemd unit installation, `docker compose …`, `git pull`, `monerod …`, `pnpm --filter @xmrswap/web build` and `@xmrswap/console build` (not re-run, so as not to replace build output others were using; the web build was run into a scratch directory instead), `@xmrswap/daemon start`, the nginx example. The start and status commands were run with the relay port and Tor port overridden, because 8787 and 9050 were in use on the build machine; the expected output in the docs shows the defaults. | |

| Q1 | WP6 (relay) | Give the Monero proxy its own budget, or exempt loopback clients: the shared 60-request default cannot carry one page's lock checks (D3). |

| Q4 | WP10 (web) | `pollMs` has no field on the Settings page; the bundle exposes it as `[ui] poll_ms`, which only helps before the first save (Q3). |
